El entorno de pruebas de API es un entorno interactivo que permite a los usuarios probar y explorar los endpoints de tu API. Los desarrolladores pueden crear solicitudes de API, enviarlas y ver las respuestas sin salir de tu documentación.

Consulta [Activar una actualización](/es/api/update/trigger) para ver un ejemplo del entorno de pruebas de API en acción.

El entorno de pruebas genera páginas interactivas para tus endpoints a partir de tu especificación OpenAPI o de tu esquema AsyncAPI. Si modificas tu API, el entorno de pruebas actualiza automáticamente las páginas correspondientes.

Te recomendamos generar tu entorno de pruebas de API a partir de una especificación OpenAPI. Sin embargo, puedes crear manualmente páginas de referencia de API después de definir una URL base y un método de autenticación en tu `docs.json`.

<div id="get-started">
  ## Primeros pasos
</div>

<Steps>
  <Step title="Añade tu archivo de especificación de OpenAPI.">
    <Tip>
      Valida tu archivo de especificación de OpenAPI con [Swagger Editor](https://editor.swagger.io/) o con el comando `mint validate` de [Mint CLI](https://www.npmjs.com/package/mint).
    </Tip>

    ```bash {3}
    /your-project
      |- docs.json
      |- openapi.json
    ```
  </Step>

  <Step title="Genera páginas de endpoints.">
    Actualiza tu `docs.json` para que haga referencia a tu especificación de OpenAPI.

    **Para generar automáticamente páginas para todos los endpoints de tu especificación de OpenAPI**, añade una propiedad `openapi` a cualquier elemento de navegación.

    Este ejemplo genera una página para cada endpoint especificado en `openapi.json` y organiza las páginas en el grupo &quot;API reference&quot;.

    ```json Generar todas las páginas de endpoints
    "navigation": {
      "groups": [
        {
          "group": "API reference",
          "openapi": "openapi.json"
        }
      ]
    }
    ```

    **Para generar páginas solo para endpoints específicos**, indica los endpoints en la propiedad `pages` del elemento de navegación.

    Este ejemplo genera páginas solo para los endpoints `GET /users` y `POST /users`. Para generar páginas de otros endpoints, añade endpoints adicionales al arreglo `pages`.

    ```json Generar páginas de endpoints específicos
    "navigation": {
      "groups": [
          {
            "group": "API reference",
            "openapi": "openapi.json",
            "pages": [
              "GET /users",
              "POST /users"
            ]
          }
      ]
    }
    ```
  </Step>
</Steps>

<div id="customize-your-playground">
  ## Personaliza tu entorno de pruebas
</div>

Personaliza tu entorno de pruebas de API definiendo las siguientes propiedades en tu `docs.json`.

<ResponseField name="playground" type="object">
  Configuración del entorno de pruebas de API.

  <Expandable title="playground" defaultOpen="True">
    <ResponseField name="display" type="&#x22;interactive&#x22; | &#x22;simple&#x22; | &#x22;none&#x22; | &#x22;auth&#x22;">
      El modo de visualización del entorno de pruebas de API.

      * `"interactive"`: Muestra el entorno de pruebas interactivo.
      * `"simple"`: Muestra un endpoint que se puede copiar, sin entorno de pruebas.
      * `"none"`: No muestra nada.
      * `"auth"`: Muestra el entorno de pruebas interactivo solo a los usuarios autenticados. Los usuarios no autenticados o que no pertenezcan a los grupos requeridos no verán ningún entorno de pruebas.

      El valor predeterminado es `interactive`.
    </ResponseField>

    <ResponseField name="proxy" type="boolean" defaultOpen="True">
      Indica si las solicitudes de API deben pasar por el servidor proxy de Mintlify. El valor predeterminado es `true`.

      Cuando es `true`, las solicitudes del entorno de pruebas se enrutan a través de los servidores de Mintlify. Cuando es `false`, el entorno de pruebas envía las solicitudes directamente desde el navegador a tu API. Establécelo en `false` cuando tu API acepte solicitudes directas desde el navegador y no necesites que Mintlify actúe como proxy. Por ejemplo, cuando tu API requiere encabezados específicos que no pueden reenviarse a través del proxy o cuando necesitas que la solicitud se origine directamente desde el navegador del usuario por motivos de autenticación.
    </ResponseField>

    <ResponseField name="credentials" type="boolean">
      Indica si se deben incluir cookies, encabezados de autorización y certificados de cliente TLS en solicitudes de origen cruzado cuando `proxy` es `false`. El valor predeterminado es `false`.

      Cuando es `true` y `proxy` es `false`, el entorno de pruebas envía las solicitudes con las credenciales administradas por el navegador. Por ejemplo, cuando tu API usa autenticación basada en cookies o tokens de sesión HTTP.

      Esta opción no tiene efecto cuando `proxy` es `true`.
    </ResponseField>
  </Expandable>
</ResponseField>

<ResponseField name="url" type="&#x22;full&#x22;">
  El modo de visualización de las URL base en los encabezados de los endpoints. Cuando se establece en `full`, se muestra la URL base completa en cada página de endpoint. De forma predeterminada, solo se muestra la ruta relativa del endpoint.
</ResponseField>

<ResponseField name="examples" type="object">
  Configuración de los ejemplos de API generados automáticamente.

  <Expandable title="examples" defaultOpen="True">
    <ResponseField name="languages" type="array of string">
      Idiomas de ejemplo para los fragmentos de API generados automáticamente.

      Los idiomas se muestran en el orden especificado.

      <Accordion title="Todos los idiomas compatibles">
        | Nombre para mostrar | Clave        | Alias                     |
        | ------------------- | ------------ | ------------------------- |
        | cURL                | `bash`       | `curl`, `sh`, `shell`     |
        | Python              | `python`     | `py`                      |
        | JavaScript          | `javascript` | `js`                      |
        | Node.js             | `node`       | `nodejs`, `node.js`       |
        | PHP                 | `php`        |                           |
        | Go                  | `go`         | `golang`                  |
        | Java                | `java`       |                           |
        | Ruby                | `ruby`       | `rb`                      |
        | PowerShell          | `powershell` |                           |
        | Swift               | `swift`      |                           |
        | C#                  | `csharp`     | `c#`                      |
        | .NET                | `dotnet`     | `.net`, `.NET`, `dot-net` |
        | TypeScript          | `typescript` | `ts`                      |
        | C                   | `c`          |                           |
        | C++                 | `c++`        | `cpp`                     |
        | Kotlin              | `kotlin`     | `kt`                      |
        | Rust                | `rust`       | `rs`                      |
        | Dart                | `dart`       | `flutter`                 |
      </Accordion>
    </ResponseField>

    <ResponseField name="defaults" type="&#x22;required&#x22; | &#x22;all&#x22;">
      Indica si deben mostrarse los parámetros opcionales en los ejemplos de API. El valor predeterminado es `all`.
    </ResponseField>

    <ResponseField name="prefill" type="boolean">
      Indica si el entorno de pruebas de API debe rellenarse previamente con datos de ejemplos del esquema. Cuando está habilitado, el entorno de pruebas completa automáticamente los campos de la solicitud con valores de ejemplo de tu especificación OpenAPI. El valor predeterminado es `false`.
    </ResponseField>

    <ResponseField name="autogenerate" type="boolean">
      Indica si se deben generar ejemplos de código para los endpoints a partir de especificaciones de API. El valor predeterminado es `true`. Cuando se establece en `false`, solo aparecen en el entorno de pruebas de API los ejemplos de código escritos manualmente (de `x-codeSamples` en especificaciones OpenAPI o componentes `<RequestExample>` en MDX).
    </ResponseField>
  </Expandable>
</ResponseField>

<div id="example-configuration">
  ### Configuración de ejemplo
</div>

Este ejemplo configura el entorno de pruebas de API para que sea interactivo y muestre fragmentos de código de ejemplo para cURL, Python y JavaScript. En los fragmentos de código, solo se muestran los parámetros obligatorios, y el entorno de pruebas rellena automáticamente el cuerpo de la solicitud con valores de ejemplo.

```json
{
 "api": {
   "playground": {
     "display": "interactive"
   },
   "examples": {
     "languages": ["curl", "python", "javascript"],
     "defaults": "required",
     "prefill": true
   }
 }
}
```

<div id="auth-based-playground-display">
  ### Visualización del entorno de pruebas según la autenticación
</div>

Usa el modo de visualización `auth` para mostrar el entorno de pruebas interactivo solo a los usuarios autenticados. Esto es útil cuando quieres permitir que los usuarios vean tu documentación de la API públicamente y, al mismo tiempo, restringir el acceso al entorno de pruebas a los usuarios que hayan iniciado sesión.

Cuando `display` se establece en `auth`:

* Los usuarios autenticados ven el entorno de pruebas interactivo.
* Los usuarios no autenticados no ven ningún entorno de pruebas (equivale a `none`).

También puedes combinar `auth` con la propiedad `groups` en el frontmatter de la página para restringir el acceso al entorno de pruebas a grupos de usuarios concretos.

```mdx Page with group-restricted playground
---
title: "Create user"
openapi: POST /users
playground: auth
groups: ["admin", "developer"]
public: true
---
```

En este ejemplo:

* La página es visible públicamente (cualquiera puede ver la documentación).
* Solo los usuarios autenticados de los grupos `admin` o `developer` ven el entorno de pruebas interactivo.
* Los usuarios que no pertenecen a esos grupos no ven ningún entorno de pruebas.

Si la página no tiene la propiedad `groups`, todos los usuarios autenticados ven el entorno de pruebas interactivo.

<Note>
  El modo de visualización `auth` requiere que tu documentación tenga la [autenticación](/es/deploy/authentication-setup) configurada.
</Note>

<div id="custom-endpoint-pages">
  ### Páginas personalizadas para endpoints
</div>

Cuando necesites un mayor control sobre la documentación de tu API, usa la extensión `x-mint` en tu especificación OpenAPI o crea páginas MDX individuales para tus endpoints.

Ambas opciones te permiten:

* Personalizar los metadatos de la página
* Añadir contenido adicional, como ejemplos
* Controlar el comportamiento del entorno de pruebas en cada página

Te recomendamos la extensión `x-mint` para que toda la documentación de tu API se genere automáticamente a partir de tu especificación OpenAPI y se mantenga en un solo archivo.

Te recomendamos páginas MDX individuales para APIs pequeñas o cuando quieras experimentar con cambios en cada página.

<div id="response-rendering">
  ## Representación de respuestas
</div>

El entorno de pruebas representa automáticamente las respuestas según el encabezado `Content-Type` que devuelve tu API.

* **Imágenes**: Se muestran en línea (`image/*`).
* **Audio**: Se reproduce con un reproductor de audio integrado (`audio/*`).
* **Video**: Se reproduce con un reproductor de video integrado (`video/*`). Cualquier respuesta con un tipo de contenido `video/*`, como `video/mp4` o `video/webm`, se muestra como un video reproducible directamente en el entorno de pruebas.
* **Todas las demás respuestas**: Se muestran en un bloque de código.

<div id="parameter-anchor-links">
  ## Enlaces de anclaje de parámetros
</div>

Cada parámetro del entorno de pruebas de API incluye un enlace de anclaje. Pasa el cursor sobre el nombre de un parámetro para que aparezca el icono del enlace y haz clic para copiar una URL directa a ese parámetro.

Usa enlaces de anclaje de parámetros para:

* Compartir enlaces a parámetros específicos en conversaciones de soporte o en la documentación
* Ir directamente a un parámetro desde otra página o recurso externo
* Guardar como marcador los parámetros que consultas con frecuencia

El formato de la URL es `your-docs-url/endpoint-path#parameter-name`. Para los parámetros anidados, el ancla incluye la ruta del parámetro principal.
