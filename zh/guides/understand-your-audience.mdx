试图面向所有人的文档，往往谁也帮不到。即使内容足够清晰、足够准确，如果它预设了错误的知识水平、使用了读者陌生的术语，或围绕读者并不关心的目标展开，依然无法发挥作用。

了解你的受众，是编写有效文档的基础。本指南将介绍如何明确你的写作对象、如何通过研究加深对他们的了解，以及如何将这些洞察应用到内容中。

<div id="define-your-primary-audience">
  ## 明确你的核心受众
</div>

每一页都应只面向一种特定类型的读者来写。如果你试图在同一篇内容中兼顾多类受众，最终往往只能做出妥协——加入让专家觉得冗长乏味的新手背景说明，或预设某些知识基础而让初学者无所适从。

常见的文档受众包括：

* **第一次接触产品的新用户**，他们需要入门引导、背景信息和分步指导
* **集成你的 API 的开发者**，他们需要技术准确性、代码示例和参考资料——而不是笼统的解释
* **配置产品的管理员**，他们需要关于设置、权限和边界情况的具体信息
* **评估产品的技术决策者**，他们需要架构概览、安全信息和能力摘要

在编写任何页面之前，先问自己：谁会阅读这篇内容？他们想完成什么？这两个问题会决定后续的每一个选择——结构、深度、语气、术语，以及哪些内容应该省略。

<div id="research-your-users">
  ## 研究你的用户
</div>

不要凭对受众的主观假设做判断。内部团队对自己的产品了解过多，很难真正代表用户。

<div id="talk-directly-to-users">
  ### 直接与用户沟通
</div>

用户访谈能带来分析无法提供的洞察。你可以问用户：

* 他们会如何用自己的话描述你的产品是做什么的？
* 他们上次查阅文档时，想要完成什么？
* 他们觉得哪些地方令人困惑，或者缺少哪些内容？
* 他们通常用什么术语来描述你产品的功能？

最后一个问题对文档尤其重要。如果用户把你的功能称为“webhook”，而你在文档中却称它为“event callback”，那么在搜索帮助时，用户就找不到你的内容——即使找到了，也意识不到它与自己的问题有关。

<div id="embed-with-your-support-team">
  ### 与支持团队密切合作
</div>

支持团队经常会遇到用户因文档问题而求助。问问他们：

* 哪些主题引发的工单最多？
* 用户最常在哪些地方感到困惑或卡住？
* 用户提到哪些内容原本以为能找到，却没有找到？

这通常是找出影响最大的文档缺口的最快方法。

<div id="use-feedback-mechanisms">
  ### 使用反馈机制
</div>

为读者提供一种渠道，让他们在发现某些内容不起作用时能够及时反馈。文档页面上的点赞/点踩评分和开放式评论框，可以帮助你了解哪些内容有效，哪些内容无效。高访问量页面上的负面反馈应当优先处理。有关如何使用反馈数据的更多信息，请参阅 [改进你的文档](/zh/guides/improving-docs)。

<div id="observe-real-navigation-behavior">
  ### 观察真实的导航行为
</div>

像 [FullStory](https://www.fullstory.com) 和 [Hotjar](https://www.hotjar.com) 这样的会话回放工具，可以准确展示用户如何浏览你的文档。用户会在哪些地方停下来、在哪些地方回滚，以及在哪些地方中途离开，这些都能反映出用户通常不会直接反馈的问题和内容缺口。

<div id="apply-what-you-learn">
  ## 学以致用
</div>

<div id="write-to-the-right-knowledge-level">
  ### 按受众的知识水平来写
</div>

根据受众已经掌握的内容来调整你的说明，而不是根据你的团队掌握的内容。

集成你的 API 的开发者不需要你解释什么是 API；但正在配置你的企业产品的非技术管理员可能需要。首次引入技术术语时，请先加以定义，并链接到更深入的说明，而不是在每一页都塞入基础背景，打断阅读体验。

```mdx
<!-- 为技术水平较低的受众在上下文中进行定义 -->
Your API key—a unique token that identifies your account—must be included in every request.

<!-- 对开发者受众跳过基础内容 -->
Include your API key in the Authorization header of every request.
```

<div id="match-terminology-to-your-audiences-vocabulary">
  ### 让术语贴近受众的用语习惯
</div>

使用用户平时会说的词。如果用户把某个东西叫作“项目”，而你的产品把它称为“工作区”，那么对于那些还没有熟悉你内部术语的人来说，你的文档读起来就会显得很陌生。写文档时，应优先使用用户会搜索的术语，再同时引入产品本身使用的术语。

<div id="adjust-depth-and-structure-to-the-task">
  ### 根据任务调整内容深度和结构
</div>

不同阶段的受众有不同的需求：

* 新用户需要引导和信心——清晰的里程碑、有限的选择，以及持续确认自己没有偏离方向
* 有经验的用户需要快速扫读——结构一致、信息密度高、上下文尽量精简
* 阅读参考文档的用户首先看重的是完整性

<div id="build-audience-awareness-into-your-process">
  ## 将受众意识融入你的流程
</div>

了解受众并不是一次性的工作。产品会变化，受众会演变，也会不断出现新的用户群体。

以下做法有助于持续更新你对受众的理解：

* **发布前，与支持团队成员一起审阅新页面。** 他们很快就能发现哪些地方的预设前提可能站不住脚。
* **在写作简报中写明对受众的假设。** 例如注明“此页面适用于已完成身份验证的开发者”，可以让评审时的写作更聚焦。
* **把新员工当作参考对象。** 在他们还没完全熟悉你们产品的内部术语前，让他们只依靠文档完成一项任务。他们的体验往往与新用户相似。

<div id="frequently-asked-questions">
  ## 常见问题
</div>

<AccordionGroup>
  <Accordion title="如果我的文档面向多类受众怎么办？">
    请为每个页面明确其主要受众，而不是试图用同一份内容满足所有人。对于确实面向不同受众的产品——也就是目标和知识水平都不同的不同用户群体——请考虑是否应划分独立的文档板块或导航路径。Mintlify 支持基于标签页的导航，无需完全拆分成多个独立文档站点，也能按受众区分内容。
  </Accordion>

  <Accordion title="如何同时为技术用户和非技术用户编写文档？">
    应分别为两类用户创建独立内容，而不是试图混在一起。面向非技术决策者的概念说明，与面向集成你产品的开发者的 API 参考，用途不同，因此应当分别成页。如果无法避免内容重叠，优先采用更技术化的版本，并为需要的读者链接到更轻量的概念性内容。
  </Accordion>

  <Accordion title="我应该多久重新评估一次对受众的判断？">
    当你发布重大产品变更、用户群体发生明显变化，或支持工单的模式出现与现有文档不匹配的变化时，就应该重新评估。按季度检查一次搜索分析和反馈数据，有助于及时发现偏差。更频繁地与支持团队沟通，则能更快发现问题。
  </Accordion>

  <Accordion title="找出文档缺口的最快方法是什么？">
    直接询问你的支持团队，哪些主题是他们最常处理、但文档覆盖不足的。这比任何分析工具都更快暴露出高影响力的内容缺口。在此基础上，再结合用户访谈、显示“无结果”查询的搜索分析，以及显示用户反复浏览页面却找不到答案的会话回放，就能获得更深入的洞察。
  </Accordion>
</AccordionGroup>
