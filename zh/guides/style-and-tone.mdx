优秀的技术文档只有一个目标：帮助用户完成任务，然后继续工作。风格和语气的选择，要么有助于实现这一目标，要么会妨碍它。清晰一致的写作能够建立用户信任；不一致或表达不清的写作则会增加理解成本，并削弱用户对产品的信心。

本指南介绍高效技术写作背后的核心原则，并提供如何将这些原则应用到实践中的具体建议。

<div id="write-in-second-person">
  ## 使用第二人称
</div>

直接用“你”来称呼用户。使用第二人称能让说明更易于理解和遵循，并使重点放在用户正在做什么，而不是产品在做什么。

```mdx
<!-- 第二人称（推荐） -->
You can configure the timeout in your settings file.

<!-- 第三人称（避免使用） -->
Users can configure the timeout in the settings file.
```

第二人称也有助于暴露被动语态：当你写下 &quot;你&quot; 时，就不得不明确谁在做什么。

<div id="use-active-voice">
  ## 使用主动语态
</div>

主动语态能让句子更简短、更清晰。被动语态中，主语是动作的承受者；主动语态中，主语发出动作。

```mdx
<!-- 主动语态 -->
The API returns an error when the token expires.

<!-- 被动语态 -->
An error is returned when the token has expired.
```

被动语态并不总是错的。当行为主体未知或不重要时，使用被动语态是合适的。但如果习惯性地默认使用被动语态，文档就会更难读。

一个快速判断方法：如果你能在动词后面加上 &quot;by zombies&quot;，这个句子就是被动语态。&quot;An error is returned [by zombies]&quot; 是被动语态。&quot;The API returns [~~by zombies~~] an error&quot; 是主动语态。

<div id="keep-sentences-and-paragraphs-short">
  ## 保持句子和段落简短
</div>

用户浏览文档时，通常是扫读而不是逐字细读。用户在查找具体答案时，长句和过于密集的段落会拖慢阅读速度。

指南：

* 尽量将句子控制在 25 个词以内
* 每个句子只表达一个意思
* 每段使用两到四个句子
* 步骤列表要用编号拆开，不要写成冗长的一大段文字

如果一个句子需要靠多个逗号或分号才能勉强连起来，那它很可能应该拆成两个句子。

<div id="use-headings-that-match-user-intent">
  ## 使用符合用户意图的标题
</div>

标题能帮助用户和搜索引擎更好地理解页面结构。撰写标题时，应回答用户可能会提出的问题，而不是从产品角度给主题命名。

```mdx
<!-- 以意图为导向（更佳） -->
## How to configure authentication

<!-- 主题标签（较弱） -->
## Authentication configuration
```

所有标题都使用句式大小写 (“Getting started”，而不是“Getting Started”) 。不要跳过标题级别——应从 H2 到 H3，而不是从 H2 直接跳到 H4。

在 Mintlify 文档中，页面的 H1 会根据 frontmatter 中的 `title:` 属性自动生成。不要在正文中手动添加 H1。

<div id="use-consistent-terminology">
  ## 使用统一的术语
</div>

为每个概念选定一个术语，并在全文中统一使用。如果用同一个意思时一会儿写 &quot;API 密钥&quot;，一会儿写 &quot;API 令牌&quot;，一会儿又写 &quot;访问令牌&quot;，用户就不得不停下来想一想你说的是不是同一回事。

首次引入某个术语时，应直接在文中给出定义，而不是链接到其他地方。

```mdx
<!-- 在上下文中定义术语 -->
Each request requires an API key—a unique token that identifies your account.

<!-- 不要假设读者有预备知识 -->
Each request requires an API key.
```

如果产品中的某些事物 (对象、操作、UI 元素) 有固定名称，请严格使用产品中的原称，并统一大小写格式。

<div id="calibrate-tone-to-your-audience-and-content-type">
  ## 根据受众和内容类型调整语气
</div>

语气应与用户想完成的任务相匹配。面向新用户的入门指南适合采用更亲切、更具鼓励性的语气。面向有经验开发者的 API 参考则应优先保证信息密度和准确性，而不是刻意营造亲和感。

以下原则适用于各种内容类型：

* **直接，但不要过于简短。** “点击保存”比“当你准备继续时，请点击保存按钮”更好。
* **避免使用无意义的套话。** “值得注意的是”“为了”“请注意”和“只需”这类表达只会增加字数，不会增加实际含义。
* **不要添加主观评价。** “这是一个强大的功能”是一种观点。应说明它的作用，而不是强调它有多出色。
* **使用用户熟悉的说法。** 如果用户称它为“webhook”，就不要在文档中称它为“事件回调”。使用他们本来就在搜索的词。

<div id="avoid-common-mistakes">
  ## 避免常见错误
</div>

<div id="jargon-and-internal-terminology">
  ### 行话和内部术语
</div>

团队内部往往会形成一些用户从未接触过的简称或说法。请检查新内容中是否包含对首次接触你们产品的人来说陌生的术语。

<div id="inconsistent-capitalization">
  ### 大小写使用不一致
</div>

确定产品功能名称是否要采用首字母大写 (如“仪表板”“API Explorer”) ，并始终保持一致。大小写使用前后不一致，会显得不够严谨。

<div id="colloquialisms">
  ### 口语表达
</div>

非正式短语和习语更难翻译，对非英语母语者来说也更难理解。面向国际受众的文档应使用简明、直接的语言。

<div id="spelling-and-grammar-errors">
  ### 拼写和语法错误
</div>

即使只有少数几个错误，也会降低内容的可信度。这会让人觉得内容没有经过认真审校，进而让用户怀疑技术内容是否也同样不可靠。

<div id="enforce-standards-with-tooling">
  ## 用工具落实标准
</div>

只有把写作原则纳入可重复执行的工作流，它们才能真正落地。以下是几种自动化执行的方法：

* **[Vale](https://vale.sh)：** 一款用于文稿的 linter，可根据可配置的写作风格规则进行检查。你可以编写规则来统一术语、标记被动语态，或捕捉常见错误。
* **[CI 检查](/zh/deploy/ci)：** 在每个拉取请求 (PR) 中运行 Vale 或其他 linter，以便在内容合并前发现风格问题。
* **现有风格指南：** 与其从零开始编写规则，不如直接基于成熟的指南。[Google Developer Documentation Style Guide](https://developers.google.com/style)、[Microsoft Style Guide](https://learn.microsoft.com/en-us/style-guide/welcome/) 和 [Splunk Style Guide](https://docs.splunk.com/Documentation/StyleGuide/current/StyleGuide/Howtouse) 都是免费且广泛使用的资源。

<Tip>
  使用[工作流](/zh/agent/workflows)，按计划或在更改推送到你的文档仓库时运行风格审查。
</Tip>

<div id="frequently-asked-questions">
  ## 常见问题
</div>

<AccordionGroup>
  <Accordion title="技术文档应该写得多正式？">
    正式程度要根据受众和产品语境来定。面向工程师的开发者工具文档可以直接、精简——省去客套，直接上代码。面向技术背景较弱的用户或企业产品的文档，通常更适合采用更温和、能预先化解困惑的语气。无论哪种情况，都要避免僵硬的企业套话。“utilize”并不比“use”更精确。写作时要像一位经验丰富的同事在解释问题，而不是像法律文件那样表述。
  </Accordion>

  <Accordion title="什么时候可以使用被动语态？">
    当动作执行者未知、不重要，或者需要强调结果而非执行者时，就可以使用被动语态。比如，如果你是在说明请求会经历什么，而不是谁来验证它，那么“The request is validated before processing”这样的表达就是合适的。被动语态的问题在于，它可能会模糊那些需要用户采取的操作究竟由谁负责。
  </Accordion>

  <Accordion title="我应该面向初学者还是专家来写？">
    先确定每一页的主要受众，再据此写作。入门指南应假定读者几乎没有前置知识。API 参考则应假定读者了解 API 的工作方式。常见错误是试图在同一页同时服务这两类人——在参考页中加入面向初学者的背景说明会拖慢专家的阅读，而在教程中假定读者具备专家知识则会让初学者跟不上。如果你确实面对两类截然不同的受众，可以考虑分别为他们提供不同类型的内容。有关指导，请参阅 [内容类型](/zh/guides/content-types)。
  </Accordion>

  <Accordion title="如何在大型文档站点中保持术语一致？">
    维护一份术语表——用一个简单的表格列出推荐术语和应避免使用的术语。把它分享给所有参与文档编写的人，并在评审时进行检查。Vale 可以通过自定义词汇表文件自动执行这些规则。维护术语表的投入很快就会见到回报：评审轮次更少，用户对术语混乱的抱怨也会减少。
  </Accordion>

  <Accordion title="文档页面多长才合适？">
    长到足以完整讲清主题，短到足以保持聚焦。如果一页涵盖两个不同的任务，可以考虑拆分。如果它只涵盖一个任务，但内容很单薄，那可能说明缺少重要细节。参考类内容可以较长且信息密集——用户通常会扫读。概念类内容应当更短——用户通常会通读。关于如何让页面长度与内容目的相匹配的更多说明，请参阅 [内容类型](/zh/guides/content-types)。
  </Accordion>
</AccordionGroup>
