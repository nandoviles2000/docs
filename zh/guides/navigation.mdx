导航决定了用户如何建立对产品的心智模型。设计良好的导航能帮助用户快速找到答案，理解产品各部分之间的关系，并确信自己来对了地方。糟糕的导航则会把用户推向搜索引擎、支持工单，或竞争对手的文档。

本指南介绍如何设计、验证和维护真正对实际用户有效的文档导航。

<div id="start-by-understanding-your-users-and-product">
  ## 先了解你的用户和产品
</div>

在组织页面之前，先与最了解你的产品和用户的人达成共识。

<div id="map-the-foundation-with-stakeholders">
  ### 与相关方一起梳理基础结构
</div>

在做出结构性决策之前，先与创始人、产品经理和工程负责人沟通。目标是了解产品实际是如何运作的，而不只是它对外如何被营销包装。

可以提出的问题：

* 用什么最简单的方式解释产品是如何运作的？
* 产品的核心构成模块是什么？
* 用户通常是如何采用这款产品的？他们最常卡在哪些地方？
* 最重要的集成或依赖项是什么？
* 如果把产品拆分成不同层级，会有哪些层级？应该按用户执行的任务来组织，还是按他们使用的功能来组织？

这些交流能帮助你梳理出产品的自然结构，也常常会揭示文档导航在哪些地方已经偏离了用户实际的思考方式。

<div id="know-who-youre-writing-for">
  ### 明确你的写作对象
</div>

导航决策取决于你的受众。集成 API 的开发者、配置设置的管理员，以及遵循引导流程的新用户，浏览和使用导航的方式都不一样。

如果你面对多个明显不同的受众，请考虑他们是否需要分别设计导航结构，还是单一的统一结构就足以满足所有人。有关如何定义文档用户画像的更多信息，请参阅[了解你的受众](/zh/guides/understand-your-audience)。

<div id="choose-a-navigation-structure">
  ## 选择导航结构
</div>

<div id="organize-by-user-journey-not-product-features">
  ### 按用户旅程组织，而不是按产品功能组织
</div>

最常见的导航错误，就是按产品团队理解产品的方式组织文档，而不是按用户实现目标的方式来组织。

以 API 产品为例，比较以下两种方式：

| 以功能为中心 (避免)  | 以旅程为中心 (更好)  |
| ------------ | ------------ |
| 核心 API       | 开始使用         |
| 身份验证         | 完成身份验证       |
| Webhooks     | 发送第一个请求      |
| 速率限制         | 处理错误         |
| SDK          | 上线生产环境       |

以旅程为中心的导航能让用户知道自己当前处于流程的哪个阶段；而以功能为中心的导航则要求用户一开始就清楚自己要找什么。

<div id="manage-depth-and-breadth">
  ### 控制层级深度和广度
</div>

导航深度是指用户需要点击几层才能找到内容；广度是指每一层显示多少个项目。

几个原则：

* **将顶层分区控制在七项以内。** 用户需要浏览和判断的选项越多，认知负担就越重。
* **深度优先于广度。** 相比 20 个顶层项目，一个包含 5 个子栏目的顶层分区更容易浏览。
* **不要把关键内容藏在两层以下。** 如果用户需要点击三层才能进入经常访问的页面，请考虑将这些内容上移。

<div id="name-navigation-items-clearly">
  ### 清晰地命名导航项
</div>

导航标签应符合用户描述自身目标的方式，而不是工程师描述功能的方式。

* 面向任务的部分使用动词 (“Authenticate”、“Deploy”、“Monitor”)
* 参考类部分使用名词 (“API 参考”、“SDKs”、“Changelog”)
* 避免使用用户无法识别的内部术语
* 保持标签简短——最好不超过 4 个词

<div id="validate-your-assumptions">
  ## 验证你的假设
</div>

你的第一版导航结构只是一个假设。在将其视为固定方案之前，先验证它。

<div id="track-real-user-journeys">
  ### 追踪真实用户路径
</div>

使用 [FullStory](https://www.fullstory.com) 或 [Hotjar](https://www.hotjar.com) 等会话回放工具，以及 [Mixpanel](https://mixpanel.com) 等分析工具，了解用户实际是如何浏览你的文档的。重点关注：

* **入口点：** 用户从哪里开始？他们是通过搜索、支持工单，还是直接从你的产品进入的？
* **导航模式：** 用户是否按照预期的信息结构浏览，还是会走出一些意料之外的路径？
* **阻碍点：** 用户会在哪些地方停下来、来回跳转，或直接结束会话？
* **搜索行为：** 用户搜索的词是否没有出现在你的导航标签中？这通常说明术语不一致。

<div id="test-with-real-users">
  ### 让真实用户参与测试
</div>

分析可以呈现出一些规律，但只有直接交流，才能了解这些规律背后的原因。

让用户只借助文档完成一项具体任务，并在过程中口述自己的思考过程。他们先点哪里、卡在哪一步，都能反映出你的导航是否足够直观。

你自己团队里的新员工也可以作为很好的用户替代对象。在他们还没因为内部接触而对产品过于熟悉之前，让他们只依靠文档去查找特定问题的答案。他们的直觉会暴露出你的导航所基于、但新手未必能察觉的那些假设。

<div id="identify-and-fix-common-problems">
  ## 识别并修复常见问题
</div>

<div id="overloaded-top-level-sections">
  ### 顶层分区过多
</div>

如果顶层导航包含超过 7 到 8 个项目，用户花在权衡选项上的时间就会多于查找内容的时间。请将相关主题归入名称清晰、便于理解的分区。

<div id="buried-essential-content">
  ### 被层层隐藏的重要内容
</div>

如果用户最需要的页面藏在两三层之后，就把它们前移。高流量页面应便于从顶层直达，或至少在相关章节的第一级中可见。

<div id="unclear-section-names">
  ### 不明确的章节名称
</div>

如果用户在点击某个导航项前会犹豫，就说明这个标签没有起到应有的作用。你可以通过描述该项包含的内容，测试用户是否能在点击前预判会看到什么。

<div id="missing-pages-vs-navigation-problems">
  ### 页面缺失与导航问题
</div>

有时，看起来像是导航问题，实际上却是内容缺失。如果用户搜索的词语与任何页面都不匹配，那么缺少的可能是内容，而不是标签命名不当。在重构之前，先区分这两种情况。

<div id="iterate-over-time">
  ## 持续迭代
</div>

导航应随着产品和用户的变化不断演进。你不必在第一次尝试时就做到尽善尽美。

一个实用的调整节奏：

* **每当产品有重大更新发布时，就检查一次导航。** 新功能往往会暴露结构上的缺口。
* **每季度查看一次搜索分析**，看看用户搜索的哪些词并未反映在导航标签中。
* **每年重新审视一次顶层结构。** 随着文档不断增加，适用于 20 个页面的结构，到了 200 个页面时可能就不再适用了。

<Tip>
  使用 [工作流](/zh/agent/workflows) 自动执行定期检查，例如找出反馈评分较低的页面，或标记很少被点击的导航项。
</Tip>

如需在 Mintlify 中配置导航 (包括标签页、分组、锚点和页面排序) ，请参阅[导航参考](/zh/organize/navigation)。

<div id="frequently-asked-questions">
  ## 常见问题
</div>

<AccordionGroup>
  <Accordion title="我应该按产品功能还是按用户目标来组织导航？">
    大多数情况下，应该按用户目标来组织。按功能划分的导航更适合已经了解产品架构的产品团队，但用户来查阅文档是为了完成某项任务，而不是浏览功能列表。应围绕用户想做的事情来组织内容，并把相关功能归到对应任务下。
  </Accordion>

  <Accordion title="顶层导航应该设置多少个部分？">
    建议控制在 5–7 个。关于认知负荷的研究表明，用户通常能较轻松地判断大约 7 个选项，再多就容易产生决策疲劳。如果超过这个数量，建议寻找可自然归类的内容，将其合并为一个部分，并在下方设置子部分。
  </Accordion>

  <Accordion title="如何处理面向多类受众的文档？">
    首先，判断这些受众是否真的需要彼此独立的结构。如果管理员和开发者都需要快速上手，共用一个“快速开始”部分，再按受众划分子部分，通常就足够了。如果他们的使用路径本质上不同——例如对应不同产品、不同角色——则可以考虑拆分为独立的文档站点，或使用基于 Tab 的导航，清晰区分这两条路径。
  </Accordion>

  <Accordion title="什么时候应该重组导航？">
    当用户数据持续显示导航存在问题时，就该重组了——例如索引页跳出率偏高、用户频繁搜索你原本预期他们能直接通过导航找到的术语，或者支持工单反映用户找不到本应很容易发现的内容。不要只凭直觉就调整导航。重组的成本是实实在在的 (例如书签失效、用户需要重新适应、内部链接需要重写) ，因此一定要确保有数据支撑。
  </Accordion>

  <Accordion title="随着文档不断增多，如何避免导航变得混乱？">
    把审核纳入内容工作流。新增页面时，在开始撰写之前就先确定它在导航中的位置。与其等到几十个页面已经积压在错误的位置后再重组，不如一开始就决定好放在哪里，这样更容易保持结构清晰一致。
  </Accordion>
</AccordionGroup>
