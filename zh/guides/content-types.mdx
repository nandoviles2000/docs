并非所有文档的作用都相同。引导新用户完成首次部署的教程，与开发者每天查阅的 API 参考，本质上是两种不同的文档。将这些不同目的混在同一页面中，只会让内容两边都顾不好。

[Diátaxis 框架](https://diataxis.fr) 提供了一套实用的方法，可根据用户当下的需求对文档进行分类。

<div id="the-four-documentation-types">
  ## 四种文档类型
</div>

<Frame>
  <img src="/images/guides/best-practices/diataxis.webp" alt="Diátaxis 框架示意图，展示了分别对应四种内容类型的四个象限：教程、操作指南、参考和解释。" />
</Frame>

<div id="tutorials-learning-oriented">
  ### 教程 (以学习为导向)
</div>

教程通过实际操作来帮助用户学习。用户的目标是学会新东西，而教程的目标是让他们顺利完成并获得成功体验——而不是罗列所有选项或解释每一处细节。

一篇好的教程应当：

* 默认用户对这项具体任务没有任何先验知识
* 从头到尾带用户完成一个完整且可运行的示例
* 尽量减少选择——明确告诉用户该怎么做，而不是提供各种备选方案
* 在关键里程碑处标明进度 (“你现在已经配置好了身份验证”)
* 只解释足够推动用户继续操作的内容，而不是面面俱到

教程是编写和维护成本最高的内容类型，但它对新用户能否成功上手你的产品有着尤为显著的影响。

<div id="how-to-guides-task-oriented">
  ### 操作指南 (以任务为导向)
</div>

操作指南帮助用户完成某个具体目标。与教程不同，它默认用户已经具备一定的背景知识，目标是完成某项特定任务，而不是学习某个概念。

一篇好的操作指南应当：

* 在标题和全文中都围绕一项具体任务展开
* 默认用户已经掌握前提条件所需的知识
* 在不加入不必要背景信息的前提下，提供清晰的步骤顺序
* 说明要做什么，而不是解释系统底层的工作原理

在实际使用中，这种与教程的区分非常重要：关于“身份验证入门”的教程会一步步带新用户走完整个流程。而关于“轮换 API 密钥”的操作指南则默认用户知道 API 密钥是什么，只需要按步骤操作。

<div id="reference-information-oriented">
  ### 参考 (信息导向)
</div>

参考文档应准确、完整地描述系统。用户查阅这类文档是为了检索信息——他们不会从头到尾阅读，也不是为了学习新知识。

优秀的参考文档应当：

* 把完整性和准确性放在首位
* 便于快速查找：使用表格、统一的格式和简短的说明
* 避免加入解释性或概念性的内容
* 覆盖所有内容，包括默认值、限制条件和边界情况
* 尽量贴近被记录对象本身的结构 (例如，API 参考应遵循 API 的结构)

API 参考、配置选项列表和 CLI 命令参考都属于参考类内容。

<div id="explanation-understanding-oriented">
  ### 解释 (以理解为导向)
</div>

解释类内容用于加深用户对某个概念的理解。当用户想明白某件事为什么会这样运作，而不是想知道如何完成某项具体任务时，他们就会阅读这类内容。

优质的解释类内容应当：

* 交代设计决策背后的背景和动机
* 说明其中的权衡取舍和可选方案
* 串联更大系统中的相关概念
* 在适当的时候明确表达观点

架构概览、概念指南以及“X 如何运作”之类的页面，都属于解释类内容。它们与操作指南的不同之处在于：读者读完一篇解释性文章后，不应该觉得自己被要求去做什么——而应该觉得自己对某件事有了更深入的理解。

<div id="choose-the-right-type-for-each-page">
  ## 为每个页面选择合适的类型
</div>

| 问题           | 教程     | 操作指南    | 参考     | 解释     |
| ------------ | ------ | ------- | ------ | ------ |
| 用户的目标是什么？    | 在实践中学习 | 解决特定问题  | 查找精确信息 | 理解某个概念 |
| 用户具备什么程度的知识？ | 初学者    | 中级      | 有经验    | 任何水平   |
| 内容是否以任务为导向？  | 是，带有引导 | 是，针对性明确 | 否      | 否      |
| 是否具有顺序性？     | 是      | 通常是     | 否      | 否      |

如果不确定某个页面适合哪种类型，问自己：“用户读完这页后会做什么？”如果他们完成了一项任务，那它就是操作指南或教程。如果他们理解了某些内容，并可能进一步在别处采取行动，那它就是解释。如果他们只是查找某个具体细节，那它就是参考。

<div id="writing-for-each-type">
  ## 各类型的写作方法
</div>

<div id="writing-tutorials">
  ### 编写教程
</div>

开头先明确预期：完成后，用户将搭建出什么，或达成什么结果？对于按顺序推进的内容，请使用 `<Steps>` 组件，并在自然的里程碑节点提示完成。尽量减少需要用户做出的选择——如果有多种可行方法，就选定一种并明确说明。

<div id="writing-how-to-guides">
  ### 编写操作指南
</div>

在标题中直接点明任务：“如何配置 Webhook”“如何从 v1 迁移到 v2”。从用户角度写作，而不是从产品角度出发。省略不影响操作步骤的背景信息。对于想进一步了解的用户，可链接到说明性内容或参考文档。

<div id="writing-reference">
  ### 编写参考文档
</div>

参考文档应围绕所描述的对象来组织，而不是围绕用户使用路径来组织。所有条目都要保持格式一致。每个参数、标志或选项都应包含类型、默认值和一行描述。确保内容便于快速查阅。

<div id="writing-explanation">
  ### 编写说明性内容
</div>

先提出你要回答的问题：“为什么身份验证要这样实现？”或“organizations 和 workspaces 有什么区别？”指出可能存在多种做法，并说明产品为什么会作出这样的选择。对于想根据所学内容继续操作的用户，请链接到操作指南。

<div id="tips-for-maintaining-type-consistency">
  ## 保持内容类型一致性的建议
</div>

* **先确定内容类型，再开始写作。** 提前定好类型，会影响后续所有写作决策——结构、篇幅、语气，以及该写什么、不该写什么。
* **检查用途混杂的页面。** 一页里同时解释概念、提供教程、再列出选项参考，既难维护，也难使用。要么拆分，要么确定一个主要类型。
* **让框架适配你的产品。** Diátaxis 是一个起点，不是一条僵化的规则。结构特殊的产品可能需要采用混合方式。其核心原则——让内容匹配用户当下的需求——具有普遍适用性。

<div id="frequently-asked-questions">
  ## 常见问题
</div>

<AccordionGroup>
  <Accordion title="每个功能都需要这四种内容类型吗？">
    不需要。较小的功能可能只需要操作指南和参考条目。这些类型描述的是用户可能会有的需求，而不是你必须完成的一份清单。应从用户的实际需求出发——通常是操作指南和参考文档——再在用户持续难以上手或理解某些内容的地方，补充教程和解释性内容。
  </Accordion>

  <Accordion title="教程和操作指南有什么区别？">
    教程是一种学习过程。用户从毫无相关知识开始，最终完成构建或某项任务，而教程本身承担了大部分教学引导。操作指南则是任务参考。用户知道自己想做什么，需要的是完成这项任务的具体步骤。关于“构建你的第一个集成”的教程和关于“连接一个新集成”的操作指南，可能涵盖相似的操作，但面向的是完全不同的用户，也适用于完全不同的场景。
  </Accordion>

  <Accordion title="单个页面可以同时承担多种内容类型吗？">
    实际情况下，页面通常会混合多种类型——尤其是同时融合教程和操作指南的入门内容。关键在于，这种混合究竟是在帮助用户，还是让用户感到困惑。如果一个页面既需要讲解概念 (解释性内容) ，又需要带用户完成设置 (教程) ，那么清晰的章节结构是可行的。如果内容混杂到难以清晰组织，通常拆分成多个独立页面会有更好的效果。
  </Accordion>

  <Accordion title="参考文档应详细到什么程度？">
    应当全面到让用户无需阅读源代码或联系支持团队，也能理解某个参数或选项。每个可配置值都应包含描述、类型、默认值和示例。省略边界情况或限制条件的参考文档，会迫使用户通过反复试错来发现这些限制——这不是用户的问题，而是文档的问题。
  </Accordion>
</AccordionGroup>
