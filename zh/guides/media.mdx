视觉媒体往往比纯文字更能清楚说明复杂工作流——但也会带来维护成本。你发布的每一张截图，都意味着当 UI 发生变化时要及时更新。每一个视频，都会在它所展示的流程发生变化后变得过时。

目标不是避免使用媒体，而是有意识地使用它，让它带来的清晰度值得你为保持内容最新所付出的维护成本。

<div id="when-to-use-media">
  ## 何时使用媒体素材
</div>

并非每个步骤都需要截图，也并非每个概念都需要图示。添加媒体素材之前，先判断它是否真的能让内容更清晰，还是简洁的文字说明和代码示例也同样足够。

<div id="screenshots">
  ### 截图
</div>

对于难以用文字说明的任务，请使用截图——尤其是在 UI 较多的工作流中，用户需要通过视觉快速定位，或者如果看不到界面，就难以准确识别应操作的界面元素时。

避免在以下情况使用截图：

* 用户几乎不可能认错的简单操作 (“点击保存”)
* 经常变化的内容——设置页面、仪表板和功能繁多的 UI 维护成本很高
* 纯装饰用途，图片本身没有提供额外信息

<div id="gifs">
  ### GIF
</div>

GIF 非常适合用于简短的循环演示——展示动画、呈现多步骤交互，或记录那些用视觉展示比逐步用文字描述更容易理解的工作流。

请让 GIF 保持简短。超过几秒的文件会变得体积很大、加载缓慢，而且较长的 GIF 也比可暂停和回看的短视频更难让用户理解。

<div id="videos">
  ### 视频
</div>

对于适合通过讲解呈现的抽象概念，或步骤顺序和时机都很关键的长工作流，请使用视频。对于复杂内容，视频比 GIF 更便于使用——用户可以暂停、回退并调节播放速度。

请将视频托管在 YouTube 或 Loom 等外部平台上，并以嵌入方式引用，而不是直接提供视频文件。视频文件会显著增加页面加载时间。

<div id="guidelines-for-every-media-type">
  ## 各类媒体的通用指南
</div>

<div id="file-format-and-size">
  ### 文件格式和大小
</div>

* 截图和图表请使用 **PNG**。PNG 可以保留清晰的边缘和文字。
* 照片或对文件大小有要求的图像请使用 **WebP**。在画质相近的情况下，WebP 比 PNG 和 JPEG 体积更小。
* 仅在必须使用动画时才使用 **GIF**。对于静态图像，GIF 相比 PNG 没有任何优势。
* 将图像添加到代码仓库之前先进行压缩。像 [Squoosh](https://squoosh.app) 这样的工具可以在几乎不影响画质的情况下减小文件大小。

<div id="dimensions">
  ### 尺寸
</div>

* 保持截图的原始分辨率，或按比例缩小；切勿放大，否则会变得模糊。
* 文档中的标准宽度通常为 800–1200px。更宽的截图会自动缩小，但在移动设备上可能会显得偏小。
* 将截图紧密裁剪到相关的 UI 区域。周围的界面边框、空白区域和无关元素都会分散读者对重点内容的注意力。

<div id="alt-text">
  ### 替代文本
</div>

每张图片都需要配有描述性的替代文本。替代文本能帮助屏幕阅读器用户理解图片内容，也有助于 SEO。

编写替代文本时，请说明图片展示了什么，以及它在当前语境下为何重要：

```mdx
<!-- 描述性且有上下文 -->
![The API keys settings page showing a list of three active keys with their creation dates and last-used timestamps](/images/api-keys-settings.png)

<!-- 无用 -->
![Settings page](/images/api-keys-settings.png)
```

关于如何编写有效的替代文本，请参阅 [无障碍访问](/zh/guides/accessibility) 了解更多。

<div id="file-naming">
  ### 文件命名
</div>

使用具有描述性的 kebab-case 文件名，以体现文件内容：

```text
api-keys-settings.png       ✓
screenshot-2024-01-15.png   ✗
image1.png                  ✗
```

使用描述性文件名能让你更容易找到并替换过时的图片，对图片 SEO 也略有帮助。

<div id="maintenance">
  ## 维护
</div>

媒体内容是文档中维护成本最高的部分。一次 UI 改版，就可能让几十张截图同时过时。

以下做法有助于减轻维护负担：

* **只裁切出相关元素。** 只展示所讨论组件的截图，比包含导航、页眉和周边 UI 的整页截图更不容易过时。
* **避免为频繁变动的内容使用截图。** 如果某个设置页面每个季度都会有 UI 变更，要考虑描述性文字是否比截图更易于维护。
* **保留源文件。** 尽可能保存未压缩的原始文件或分层文件，这样更新截图时就无需从头重新截取。
* **记录每张图片展示的内容。** 在 MDX 中添加注释，或维护一份共享图片清单来注明每张图片展示的内容，都能帮助你在审查时更快识别出过时的资源文件。

<div id="frequently-asked-questions">
  ## 常见问题
</div>

<AccordionGroup>
  <Accordion title="分步说明应该用截图还是文字？">
    应以文字为主，截图作为补充，而不是替代。文字更便于快速浏览、更易搜索，更新成本也更低。只有当用户需要在 UI 中直观识别某个元素，或某个工作流不看图确实容易让人困惑时，再添加截图。常见做法是先用文字说明步骤，只在需要视觉定位的步骤中加入截图。
  </Accordion>

  <Accordion title="UI 更新时，该如何处理截图？">
    最快的方法是重新截取实际发生变化的那些截图，而不是一次性批量更新所有截图。裁剪紧凑、只聚焦单个元素的截图，比整页截图更不容易过时。遇到重大 UI 改版上线时，应将截图更新视为一次范围明确的文档冲刺，而不是长期持续的干扰。
  </Accordion>

  <Accordion title="使用 GIF 和短视频有什么区别？">
    GIF 会自动循环，无需用户交互，也能直接嵌入页面，无需播放器。它适合简单、时长较短，且循环播放有帮助的交互。短视频更适合时长超过几秒的内容、需要音频辅助的内容，或复杂到用户需要暂停并查看特定画面的工作流。视频在无障碍支持方面也更好——GIF 无法暂停，除在周边内容中添加描述外，也没有与替代文本等效的机制。
  </Accordion>

  <Accordion title="如果图片只是装饰性的，还需要替代文本吗？">
    如果图片不传达任何信息——例如纯装饰性的分隔元素或背景元素——请使用空的 alt 属性 (`alt=""`) ，告诉屏幕阅读器跳过它。但文档中的大多数图片都是信息性的，不是装饰性的。如果拿不准，就写替代文本。
  </Accordion>
</AccordionGroup>
