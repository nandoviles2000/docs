Git 是一种版本控制系统，可跟踪文档的变更并支持团队协作。借助 Git，你可以查看文件随着时间推移发生了哪些变化、这些变化由谁做出、发生在何时，以及为什么会有这些变化。如果你需要撤销更改，Git 还能让你轻松恢复到文件的早期版本。

网页编辑器会在后台执行 Git 操作。了解 Git 后，你就能更高效地使用网页编辑器，并与采用本地开发方式的团队成员协作。

<div id="why-git-for-documentation">
  ## 为什么文档要使用 Git？
</div>

Git 为文档管理提供了必不可少的能力。

* **版本历史**：查看每个文件改了什么、何时修改，以及为什么修改。
* **协作**：多人可以同时处理文档的不同部分。
* **安全性**：放心试验，而不会影响线上文档。
* **审查工作流**：团队成员可以在发布前审查更改。
* **恢复**：撤销错误或恢复到之前的版本。

<div id="new-to-git">
  ## 刚接触 Git？
</div>

如果你对 Git 和版本控制还完全陌生，可以按下面的路径开始上手。

<Steps>
  <Step title="先使用网页编辑器。">
    [网页编辑器](/zh/editor/index)会自动处理 Git 操作。

    * 你在修改内容时，可以直观地看到每一处变更。
    * 一键创建分支。
    * 无需使用 Git 命令即可发布并创建拉取请求 (PR) 。

    这样你无需使用命令行，也能逐步理解 Git 的核心概念。
  </Step>

  <Step title="边做边学。">
    当你使用网页编辑器时，其实就是在使用 Git。

    * **保存更改**会创建一次提交。
    * **创建分支**会创建一个 Git 分支。
    * **发布**会发起一个拉取请求 (PR) 供审核。
  </Step>

  <Step title="在需要时再尝试本地开发。">
    你可以完全通过网页编辑器和仪表板来管理文档，也可以在本地环境中工作，自定义自己的工作流。

    * 在你常用的编辑器中创建和编辑文件。
    * 使用命令行 Git、GitHub Desktop，或编辑器中的扩展。
    * 在发布前先在本地预览更改。
    * 与支持工单、问题跟踪和设计系统等其他工具集成。
  </Step>
</Steps>

<div id="core-git-concepts">
  ## Git 核心概念
</div>

<AccordionGroup>
  <Accordion title="分支">
    分支指向仓库中的某个特定提交。你的线上文档由部署分支构建而成。你还可以创建任意数量的其他分支，这些分支中的更改在发布到线上文档之前都不会生效。如果你想把某个分支中的更改合并到线上文档中，可以通过拉取请求 (PR) 将该分支合并到部署分支。

    使用分支可以在不影响线上文档的情况下进行修改、安全地试验新功能，并在发布前获得审查。
  </Accordion>

  <Accordion title="克隆">
    将仓库的完整副本下载到你的计算机中，包括所有文件和完整的历史记录。克隆后，你就拥有了在本地开展工作所需的全部内容。

    ```bash
    git clone https://github.com/your-org/your-repo
    ```
  </Accordion>

  <Accordion title="提交">
    在某个特定时间点保存的更改快照。每次提交都包含一条说明更改内容的消息，并在项目历史中留下永久记录。
  </Accordion>

  <Accordion title="冲突">
    当两个人以不同方式修改文件的同一部分时，就会发生冲突。Git 会要求你手动选择保留哪一项更改，或将两项更改合并起来。
  </Accordion>

  <Accordion title="部署分支">
    项目的主要分支。对此分支的更改会自动发布到你的文档站点。它通常叫做 `main`，但你也可以将任意分支设为部署分支。
  </Accordion>

  <Accordion title="差异">
    差异 (diff 或 difference) 显示同一文件两个版本之间的变化。在审查拉取请求 (PR) 时，差异会突出显示文件相较原始版本有哪些不同。
  </Accordion>

  <Accordion title="合并">
    将一个分支中的更改合并到另一个分支。通常是在审查后通过拉取请求 (PR) 完成，以将功能开发的成果纳入部署分支。
  </Accordion>

  <Accordion title="拉取">
    将远程仓库中的最新更改获取到本地副本，让你的本地内容与其他人的工作保持同步。

    ```bash
    git pull
    ```
  </Accordion>

  <Accordion title="拉取请求（PR）">
    一种提议将你在某个分支上的更改合并到线上文档中的方式。它支持在更改上线前进行审查和讨论。通常简称为 PR，在 GitLab 中也称为 merge request。
  </Accordion>

  <Accordion title="推送">
    将你的本地提交发送到远程仓库。这会让其他人可以获取你的更改，也可能触发自动部署。

    ```bash
    git push
    ```
  </Accordion>

  <Accordion title="远程仓库">
    托管在服务器上的仓库版本。你的本地仓库会连接到远程仓库，以便推送和拉取更改。
  </Accordion>

  <Accordion title="仓库">
    包含文档站点页面所需全部文件及其历史记录的文档源代码。网页编辑器会连接到你的文档仓库，以访问和修改内容。
  </Accordion>

  <Accordion title="暂存">
    准备要包含在下一次提交中的特定更改。暂存让你可以将更改整理成逻辑清晰的提交。

    ```bash
    git add filename.mdx
    ```
  </Accordion>
</AccordionGroup>

<div id="how-the-web-editor-uses-git">
  ## 网页编辑器如何使用 Git
</div>

网页编辑器通过 [GitHub App](/zh/deploy/github) 或 [GitLab 集成](/zh/deploy/gitlab) 连接到你的 Git 仓库，并自动处理常见的 Git 操作。

当你：

* **打开文件**：编辑器会从仓库中获取最新版本，确保你始终处理的是最新内容。
* **进行更改**：编辑器会将你的更改记录为草稿，你准备好保存时即可将其转为一次提交。
* **保存更改**：编辑器会根据你的更改创建一次提交，将你的工作保存在项目历史记录中。
* **创建分支**：编辑器会在你的仓库中创建一个新分支，任何有权访问该仓库的人都可以使用该分支协作并审查更改。
* **在部署分支上发布**：编辑器会直接提交并推送到你的部署分支，立即发布你的更改。
* **在其他分支上发布**：编辑器会创建一个拉取请求 (PR) ，让你在将更改合并到部署分支之前先获得他人的反馈。

<div id="common-workflows">
  ## 常见工作流
</div>

<div id="publish-directly-to-your-deployment-branch">
  ### 直接发布到部署分支
</div>

<Tabs>
  <Tab title="使用网页编辑器">
    1. 在[网页编辑器](https://dashboard.mintlify.com/editor)中打开文件。
    2. 进行修改。
    3. 点击 **Publish**。
    4. 更改会显示在仓库中，并自动部署。
  </Tab>

  <Tab title="使用本地开发">
    1. 拉取最新更改：`git pull`
    2. 在编辑器中编辑文件。
    3. 暂存更改：`git add filename.mdx`
    4. 提交：`git commit -m "Update documentation"`
    5. 推送：`git push`
    6. 更改会自动部署。
  </Tab>
</Tabs>

<div id="work-on-a-feature-branch">
  ### 在功能分支上进行开发
</div>

<Tabs>
  <Tab title="使用网页编辑器">
    <Note>
      要通过网页编辑器创建拉取请求 (PR) ，你必须启用分支保护规则，要求更改在合并到部署分支之前先发起拉取请求 (PR) 。如果没有分支保护规则，分支上的更改会在发布时直接合并到部署分支。
    </Note>

    1. 在编辑器工具栏的分支下拉菜单中创建分支。
    2. 在该分支上进行更改并保存。
    3. 点击 **Publish** 以创建拉取请求 (PR) 。
    4. 准备就绪后，合并拉取请求 (PR) 。
  </Tab>

  <Tab title="使用本地开发">
    1. 创建分支：`git checkout -b feature-name`
    2. 进行更改并提交。
    3. 推送分支：`git push -u origin feature-name`
    4. 创建拉取请求 (PR) 。
    5. 准备就绪后，合并拉取请求 (PR) 。
  </Tab>
</Tabs>

<div id="review-changes-before-publishing">
  ### 发布前先审查更改
</div>

<Steps>
  <Step title="创建功能分支。">
    在独立于部署分支的分支中进行更改，以便在发布前共享并审查这些更改。
  </Step>

  <Step title="进行更改。">
    编辑文件，并将更改提交到功能分支。
  </Step>

  <Step title="创建拉取请求（PR）。">
    创建拉取请求 (PR) ，提议将功能分支上的更改合并到部署分支。
  </Step>

  <Step title="查看差异。">
    检查你的更改。拉取请求 (PR) 会显示该文件相对于原始版本的逐行差异。
  </Step>

  <Step title="获取团队反馈。">
    团队成员可以对特定行或整体更改提出评论。根据反馈进行修改，并将这些更改提交到功能分支。
  </Step>

  <Step title="获批后合并。">
    合并拉取请求 (PR) ，将更改发布到你的线上文档。
  </Step>
</Steps>

<div id="git-best-practices">
  ## Git 最佳实践
</div>

每个团队都会形成自己的工作流和偏好，但你可以先从以下这些通用最佳实践入手。

* **编写清晰的提交信息**：使用主动语态，具体说明变更内容。`Fix broken link in API docs` 比 `update page` 更清楚。
* **使用清晰的分支名称**：分支名称应说明分支的用途。请使用像 `update-api-reference` 这样含义明确的名称，而不要使用 `temp` 或 `my-branch` 这类笼统的名称。
* **保持分支聚焦**：将分支中的更改集中在某个特定任务或项目上。这样可以让审查更轻松，并减少冲突。
* **合并后删除分支**：当你不再需要某个分支时，请将其删除，以保持仓库整洁。
* **推送前先拉取**：推送前务必先拉取最新更改，以避免冲突。网页编辑器会自动执行此操作。
* **先审查自己的更改**：创建拉取请求 (PR) 之前，先检查差异。
