Git 可让您管理并跟踪文件变更。在 docs-as-code 工作流中，Git 是首选的版本控制系统，您可以像管理其他任何代码库一样管理文档。

网页编辑器会为您处理 Git 操作。了解几个关键概念，有助于您充分发挥编辑器的作用并与团队协作。

<div id="what-git-does-for-your-docs">
  ## Git 如何管理你的文档
</div>

Git 会跟踪文档的每一次变更。它会记录改了什么、是谁改的、何时修改，以及为什么修改。这意味着你可以：

* 查看任意页面的完整历史记录。
* 回退到之前的版本，撤销更改。
* 在不影响线上站点的情况下处理更新。
* 在更改上线前先进行审查。

你的文档仓库是构成文档站点的所有文件及其历史记录的集合。网页编辑器会连接到这个仓库，读取并更新你的内容。

<div id="key-concepts">
  ## 关键概念
</div>

以下是你在使用网页编辑器时最常遇到的 Git 概念。

<AccordionGroup>
  <Accordion title="提交">
    在某个时间点保存的变更快照。每次提交都会附带一条说明变更内容的消息，并在项目历史中留下永久记录。

    当你保存更改时，网页编辑器会创建一次提交。
  </Accordion>

  <Accordion title="分支">
    仓库中一条独立的工作线，也称为 **功能分支**。

    你的线上文档站点由 **部署分支** 构建，通常名为 `main`。其他分支让你可以独立处理更改。在你通过拉取请求（PR）将分支合并到部署分支之前，该分支上的任何内容都不会影响你的线上站点。

    当你创建分支时，网页编辑器会在仓库中创建一个新分支。你可以通过工具栏中的分支下拉菜单搜索和切换分支。如果你有未保存的更改，编辑器会让你选择将它们带到新分支，或保留在当前分支中。
  </Accordion>

  <Accordion title="部署分支">
    用于构建线上文档站点的分支，通常名为 `main`。合并到此分支的更改会自动部署到你的站点。
  </Accordion>

  <Accordion title="拉取请求（PR）">
    将一个分支中的更改合并到另一个分支的提议。拉取请求（PR）让你的团队可以在更改上线前进行审查和讨论。

    当你在功能分支上发布更改时，网页编辑器会创建一个拉取请求（PR）。你的团队会在 Git 提供商 (GitHub 或 GitLab) 中审查并合并该拉取请求（PR）。
  </Accordion>

  <Accordion title="合并">
    将一个分支中的更改合并到另一个分支。团队审查并批准拉取请求（PR）后，合并分支会将你的更改纳入部署分支并发布。
  </Accordion>

  <Accordion title="冲突">
    当两个人以不同方式修改文件的同一部分时，就会发生冲突。编辑器会帮助你解决分支上出现的冲突。
  </Accordion>

  <Accordion title="差异">
    用于显示文件两个版本之间差异的对比视图。在审查拉取请求（PR）时，差异会清楚标出具体改动。网页编辑器可以在你发布前审查分支更改时显示单个文件的差异。
  </Accordion>
</AccordionGroup>

<div id="how-the-editor-maps-to-git">
  ## 编辑器如何对应 Git
</div>

你在网页编辑器中执行的每项操作，都对应一个 Git 操作。

| 你在编辑器中的操作 | 后台对应的 Git 操作                                |
| --------- | ------------------------------------------- |
| 打开文件      | 从你的仓库获取最新版本                                 |
| 保存更改      | 创建一个**提交**，即项目历史记录中你所做更改的快照                 |
| 创建分支      | 创建一个**分支**，也就是一条独立的工作线；除非你选择发布，否则不会影响你的线上站点 |
| 在部署分支上发布  | 直接推送你的提交，从而触发部署                             |
| 在功能分支上发布  | 创建一个**拉取请求（PR）&#x20;**，即提议将你的更改合并到部署分支     |
