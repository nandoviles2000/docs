<Info>
  工作流目前处于 Beta 阶段。在 Beta 期间，所有套餐均可免费使用。工作流功能、可用性和定价都可能发生变化。
</Info>

工作流可以按计划自动运行智能体，也可以在代码库发生 push 时触发运行。每个工作流都会定义一个供智能体执行的提示词，以及一个触发运行时机的触发条件。工作流同时支持 GitHub 和 GitLab 代码库。

工作流运行时，智能体会克隆所有指定的代码库作为上下文，按照提示词执行，并创建拉取请求 (PR)  (对于 GitLab，则为合并请求) ，或者直接将更改推送到你的部署分支。

每个工作流每天最多可运行 50 次。运行失败不计入此限制。

<Tip>
  使用按计划运行的工作流，可以自动化处理发布更新日志或检查语法和风格问题等周期性任务。

  使用在 push 事件时运行的工作流，可以自动化处理更新 API 参考或识别新功能所需文档更新等响应式维护任务。
</Tip>

<div id="create-a-workflow">
  ## 创建工作流
</div>

1. 打开 [工作流](https://dashboard.mintlify.com/products/workflows) 页面。
2. 点击 **新建工作流**。
3. 配置工作流名称、触发类型、仓库和计划时间。
4. 编写智能体指令，并选择是否自动合并拉取请求 (PR) 。
5. 可选：启用 Slack 通知，以便在工作流完成时接收提醒。
6. 点击 **创建工作流**。

  ## 配置
</div>

| 字段       | 必填 | 描述                                                   |
| -------- | -- | ---------------------------------------------------- |
| **名称**   | 是  | 在仪表板中显示的名称。                                          |
| **触发器**  | 是  | 触发器配置。                                               |
| **上下文**  | 否  | 工作流运行时会克隆这些仓库作为参考。                                   |
| **自动合并** | 否  | 默认为关闭，此时会创建一个拉取请求 (PR) 供审核。启用后，会创建一个拉取请求 (PR) 并自动合并。 |
| **通知**   | 否  | 通知配置。在工作流完成时发送 Slack 消息。                             |

<div id="triggers">
  ### 触发器
</div>

每个工作流必须且只能定义一个触发器。

<div id="on-schedule-cron">
  #### 按计划 (cron)
</div>

使用 cron 表达式按固定计划重复运行工作流。所有计划均使用 UTC。

工作流会在计划时间后的 10 分钟内进入队列，且开始运行最多还可能需要 10 分钟。

该值为标准的 5 字段 cron 表达式，格式为 `minute hour day-of-month month day-of-week`。使用 [crontab.guru](https://crontab.guru) 等工具来创建并验证计划。

| 表达式           | 计划              |
| ------------- | --------------- |
| `0 9 * * 1`   | 每周一 UTC 上午 9:00 |
| `0 0 1 * *`   | 每月第一天 UTC 午夜    |
| `0 8 * * 1-5` | 工作日 UTC 上午 8:00 |

<div id="on-push-events">
  #### 在 push 事件中
</div>

当变更被推送到特定仓库或分支时，运行工作流。这包括拉取请求 (PR) 合并，以及直接推送到该分支这两种情况。

以 `owner/repo` 格式指定每个仓库。你也可以选择指定要监控的分支。如果未指定分支，工作流会在推送到仓库的默认分支时触发。

一个工作流最多可监控 10 个仓库或分支上的推送。

<div id="context-repositories">
  ### 上下文仓库
</div>

上下文仓库可在工作流运行时让智能体对其他仓库拥有只读访问权限。当你的提示需要审查文档仓库之外的代码或内容时，这会非常有用。每个工作流最多可指定五个上下文仓库。

<div id="auto-merge-changes">
  ### 自动合并更改
</div>

默认情况下，智能体会为每次工作流运行创建一个拉取请求 (PR) ，以便你在更改生效前先进行审核。启用自动合并后，系统会自动合并该拉取请求 (PR) ，无需手动批准。这样既能在仓库的拉取请求历史中保留变更记录，又能自动完成合并这一步骤。

<Note>
  对于 GitHub 仓库，自动合并要求 Mintlify GitHub App 对所有以你的部署分支为目标的规则集都拥有绕过权限，包括组织级和仓库级规则集。设置说明请参阅[配置自动合并](/zh/guides/configure-automerge)。

  对于 GitLab 仓库，自动合并使用你在 Mintlify 仪表板的 [GitLab OAuth](https://dashboard.mintlify.com/settings/organization/gitlab-oauth) 页面上配置的 GitLab OAuth 连接。你必须在每个项目中至少具有 Maintainer 角色，才能连接 GitLab OAuth。
</Note>

<div id="slack-notifications">
  ### Slack 通知
</div>

在工作流完成或失败时发送 Slack 消息。通知将包含工作流状态、拉取请求 (PR) 链接以及变更摘要。

<Note>
  Slack 通知要求在您所在组织的 Slack 工作区中安装 Mintlify Slack 应用。请前往您的[仪表板](https://dashboard.mintlify.com/products/agent)安装该 Slack 应用。
</Note>

在仪表板中创建或编辑工作流时，可在 **Notify on completion** 开关下启用 Slack 通知：

1. 如果您尚未连接 Slack，请点击 **Install Slack app**。
2. 点击 **Notify on completion** 开关。
3. 搜索并选择要通知的频道。
4. 保存工作流。

<div id="manage-workflows">
  ## 管理工作流
</div>

你可以在仪表板的 [工作流](https://dashboard.mintlify.com/products/workflows) 页面中编辑、删除、禁用或触发工作流。

<div id="trigger-a-workflow-manually">
  ### 手动触发工作流
</div>

你可以按需运行基于 cron 的工作流，无需等待下一个计划执行时间。手动触发的运行也会计入每日运行次数上限。

1. 前往仪表板中的 [Workflows](https://dashboard.mintlify.com/products/workflows) 页面。
2. 点击 **View workflows**，查看所有工作流。
3. 点击你要运行的工作流。
4. 点击 <Icon icon="play" /> 手动触发工作流按钮。

<div id="disable-a-workflow">
  ### 禁用工作流
</div>

禁用工作流后，你可以在不删除它的情况下暂时停止其运行。已禁用的工作流会保留其配置和运行历史记录，但不会按计划运行，也不会响应 push 事件。你也无法手动触发已禁用的工作流。

如需切换工作流状态：

1. 前往仪表板中的 [Workflows](https://dashboard.mintlify.com/products/workflows) 页面。
2. 点击 **View workflows**，查看所有工作流。
3. 点击要禁用或启用的工作流。
4. 关闭 **Active** 切换开关以禁用工作流，或将其打开以启用工作流。
5. 点击 **Save changes**。

重新启用基于 cron 的工作流后，Mintlify 会从当前时间起重新计算下一次运行时间。

<div id="gitlab-setup">
  ## GitLab 设置
</div>

要在工作流中使用 GitLab 仓库，请在 GitLab OAuth 设置页面中，通过 GitLab OAuth 集成连接各个项目。你必须连接工作流会涉及的每个仓库，包括文档仓库以及任何触发仓库或上下文仓库。

<Note>
  工作流需要 GitLab 的付费套餐。智能体会使用短时有效的项目访问令牌来访问仓库，而 GitLab 的 Free 套餐不支持这一功能。
</Note>

<div id="prompts">
  ## 提示词
</div>

有效的提示词应聚焦于单一任务，并以明确的结果为目标。由于智能体具有非确定性，工作流的输出总会存在一定波动，但你可以遵循以下最佳实践来提高输出的一致性。

* 描述你希望智能体达成的结果。
* 包含成功标准。
* 明确你希望智能体使用的上下文。
* 将复杂任务拆分为多个步骤或多个工作流。

<div id="agent-environment">
  ### 代理运行环境
</div>

代理在隔离的沙箱中运行。编写提示词时，只能提及代理可用的工具。

* 标准 shell 实用工具 (`grep`、`sed`、`awk`、`curl` 等)
* `git` 和 GitHub CLI (`gh`)
* Mintlify CLI (`mint`)
* Node.js 和 Bun
* 用于查找文档之外最新信息的**网络搜索**
* 用于获取并读取网页内容的**网页获取**

代理无法在运行时安装额外的软件包或工具。沙箱无法访问包注册表。

如果提示词要求代理运行不可用的工具，可能会产生意外结果或直接失败。

<div id="draft-documentation-for-new-features">
  ### 为新功能生成文档草稿
</div>

<Tip>
  如果你在仪表板中使用智能体建议，这个工作流会复现相同的行为。

  根据项目需求修改并添加此工作流后，当你为产品添加新功能时，系统就会自动生成文档草稿。
</Tip>

**触发条件：** 推送到 `your-org/your-product` 时 (`main` 分支)
**上下文仓库：** `your-org/your-docs`

```text
查看 `your-org/your-product` 中最近合并的 PR（拉取请求）的差异。识别所有需要编写文档的新功能、API 或其他变更。

针对每项新增内容，起草文档更新，说明其功能、适用场景及配置方法。如有必要，附上代码示例。

成功标准：用户阅读新增或更新的文档后，能够理解该功能的用途、是否适用于自身的工作任务，以及如何使用。

## 重要说明

- 仅记录影响最终用户的变更，跳过内部重构或依赖项更新。
- 保持与现有文档页面一致的风格和结构。
```

<div id="style-audit">
  ### 样式审核
</div>

**触发条件：** 当推送到 `your-org/your-docs` (main 分支) 时

```text
Review all MDX files changed in the last merged PR against the style guide at `path/to/style-guide`.

Open a pull request to resolve any style violations that can be fixed automatically. For any edits that require judgment or nuance, note them in the PR body with the specific lines, rule violations, and suggested fixes.

Success criteria:
- All style violations have a proposed resolution.
- No new style violations are introduced.

## Important

- Do not change content meaning. Only correct style violations.
- Skip any files in language subdirectories (`es/`, `fr/`, `zh/`).
```

<div id="update-api-reference">
  ### Update API 参考
</div>

**触发条件：** 推送到 `your-org/your-product` (`main` 分支)
**上下文仓库：** `your-org/your-docs`

```text
查看 `your-org/your-product` 中最近合并的 PR 的差异，检查 API endpoint、参数、响应结构或错误码是否有变更。

更新文档中对应的 API 规范或页面，以反映上述变更。在受影响处补充更新后的参数描述、类型信息和示例。

成功标准：所有 API 规范和页面均已与产品仓库中的变更保持同步。

## 重要说明

- 如果某个参数或 endpoint 被移除，请将其标记为已弃用，而非直接删除——除非代码明确将其移除且未设置任何弃用过渡期。
- 如果未引入任何 API 变更，则无需进行任何操作。
```

<div id="track-translation-lag">
  ### 跟踪翻译延迟
</div>

**触发器：**Cron 计划 `0 9 * * 3` (UTC 时间每周三上午 9:00)

将示例语言子目录 (`es/`、`fr/`、`zh/`) 替换为你的实际语言子目录。

```text
将仓库中的英文 MDX 文件与 `es/`、`fr/` 和 `zh/` 子目录中的对应翻译文件进行比对。使用 git 历史记录找出英文版本比翻译版本更新的文件。

提交一个拉取请求（PR），按语言分类列出不同步的页面。对于每个页面，注明英文版最后更新的日期，并简要说明变更内容，帮助译者了解需要更新哪些内容。

成功标准：英文文件与翻译文件之间的所有差异均已识别，并列于拉取请求（PR）中。

## 重要说明

- 如果翻译文件不存在，将其标记为缺失，而非不同步。
- 按语言对结果进行分组，再按滞后程度排序（最滞后的优先）。
```

<div id="seo-and-metadata-audit">
  ### SEO 和元数据审核
</div>

**触发条件：** Cron 计划 `0 9 * * 1` (每周一 UTC 时间上午 9:00)

```text
审查文档中所有 MDX 文件的 SEO 和元数据质量。检查以下问题：

- 缺失或为空的 `title` frontmatter
- 标题过长（超过 60 个字符）——过长的标题会在搜索结果摘要中被截断
- 标题套用"页面类型 - 名称"等模板格式，未能描述页面的具体内容
- 缺失或为空的 `description` frontmatter（请参阅下方 OpenAPI 页面说明——当 OpenAPI 规范提供描述时，不应视为缺失）
- 描述过短（少于 130 个字符）——过短的描述通常会被 Google 忽略，转而使用自动生成的摘要
- 描述过长（超过 160 个字符）
- 与其他页面使用相同描述的页面——每个页面需要有唯一的描述

针对发现的问题，提交一个包含改进内容的拉取请求（PR）。

撰写标题时：具体描述页面所涵盖的内容，避免使用"概述 - 产品名称"等通用格式。目标长度为 50-60 个字符。

撰写描述时：用简洁的语言概括该页面的具体内容，包含 2-3 个用户实际会搜索的词语，切勿在多个页面中重复使用相同的描述。目标长度为 130-155 个字符。

### frontmatter 中包含 `openapi:` 的页面（来自规范的 API 参考）

`openapi:` frontmatter 的值可以是**操作引用**（例如 `openapi: GET /users/{id}`）或**文件引用**（例如 `openapi: ./openapi.yaml`）。只有操作引用才会从规范中为每个页面提供 `summary` 和 `description`。

对于使用**操作引用**的页面：
- 读取所引用的 OpenAPI 规范文件，检查该操作是否定义了 `description`。
- 如果该操作**已有** `description`：不要在 frontmatter 中添加 `description:` 字段。如果之前错误地添加了，请将其删除，以便元数据来自规范。
- 如果该操作**没有** `description`：按常规方式审查 `description` frontmatter——缺失则添加，不符合质量要求则修正。
- 如果该操作定义了 `summary` 且页面没有 `title:` frontmatter，则视标题为已存在——不要添加。
- 切勿编辑 OpenAPI 规范文件本身。

对于使用**文件引用**的页面，按常规方式审查所有 frontmatter 字段。

成功标准：
- 页面具有唯一标题，长度不超过 60 个字符，且能描述具体内容
- 页面具有唯一描述，长度在 130 到 160 个字符之间（OpenAPI 规范提供描述的页面除外）

## 重要说明

- 仅更新 frontmatter，不得修改页面内容或 OpenAPI 规范文件。
- 如果所有页面的元数据均完整且合理，则无需执行任何操作。
```

<div id="changelog-with-notifications">
  ### 带通知的变更日志
</div>

**触发条件：** Cron 计划 `0 9 * * 1` (UTC 时间每周一上午 9:00)
**上下文仓库：** `your-org/your-product`
**Slack 通知：** `documentation` 频道、`tech-writer` 用户

```text
审查过去一周内 `your-org/your-product` 中所有已合并的 PR（拉取请求）。起草一篇变更日志，概述新功能、错误修复和重大变更。

成功标准：变更日志准确反映本周的变更内容，并已准备好供审阅。
```
