Créez un fichier `.mintlify/AGENTS.md` à la racine de votre projet de documentation pour personnaliser le comportement de l’agent (`Agents.md` est aussi un nom de fichier accepté).

<Warning>
  Placez votre fichier `AGENTS.md` dans le répertoire `.mintlify/`, et non à la racine de votre projet. Si vous stockez le fichier à la racine de votre projet, vos instructions personnalisées seront accessibles publiquement via le chemin `/agents.md`. Le répertoire `.mintlify/` n’est pas exposé publiquement, donc votre fichier `AGENTS.md` n’est pas accessible lorsqu’il s’y trouve.

  Si vous devez stocker votre fichier `AGENTS.md` à la racine de votre projet ou dans un autre répertoire, ajoutez-le à votre fichier [`.mintignore`](/fr/organize/mintignore) pour l’exclure de votre site de documentation.
</Warning>

Ajoutez toutes les instructions que vous voulez que l’agent suive. L’agent ajoute ces instructions à son prompt système ; elles s’appliquent donc à toutes les tâches, que vous utilisiez l’agent dans votre tableau de bord, sur Slack ou via l’API.

<div id="what-to-include-in-agentsmd">
  ## Que faut-il inclure dans AGENTS.md
</div>

Pensez à ajouter des instructions sur les points suivants :

* **Préférences de style** : la voix, le ton, la mise en forme et la terminologie propres à votre documentation.
* **Normes de code** : les langages de programmation, les frameworks et les conventions de codage à utiliser dans les exemples.
* **Exigences de contenu** : les sections ou informations à inclure selon les différents types de pages.
* **Contexte du projet** : des détails spécifiques sur votre produit, votre architecture ou votre base d’utilisateurs, qui orientent les décisions en matière de documentation.

<div id="example-agentsmd-file">
  ## Exemple de fichier AGENTS.md
</div>

```markdown .mintlify/AGENTS.md
# Instructions pour l'agent de documentation

## Exemples de code
- Utiliser TypeScript pour tous les exemples de code. Nos utilisateurs sont principalement des développeurs TypeScript.
- Toujours inclure la gestion des erreurs dans les exemples d'appels API.
- Fournir des exemples de réponses en cas de succès et d'erreur pour tous les points de terminaison.
- Inclure les instructions d'importation en haut des exemples de code.

## Normes de documentation API
- Chaque point de terminaison doit documenter : les exigences d'authentification, les limites de débit et les codes d'erreur courants.
- Utiliser des valeurs de paramètres réalistes dans les exemples (pas de valeurs fictives comme foo/bar).
- Inclure un cycle requête/réponse complet pour chaque point de terminaison.

## Style et mise en forme
- Écrire pour des développeurs ayant 2 à 5 ans d'expérience. Ne pas trop simplifier, mais expliquer les concepts non évidents.
- Utiliser la voix active et la deuxième personne (« vous »).
- Format de date : ISO 8601 (YYYY-MM-DD).
- Pour les références aux éléments d'interface, utiliser le gras : bouton **Settings**.

## Ce qu'il faut inclure
- Ajouter des sections de prérequis aux guides lorsque les utilisateurs ont besoin de clés API, d'une configuration d'environnement ou de dépendances.
- Inclure des sections « Étapes suivantes » avec des liens vers la documentation connexe.
- Ajouter des sections de dépannage pour les problèmes courants remontés dans les tickets de support.
```
