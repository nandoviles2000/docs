Si vos pages API ne s’affichent pas correctement, vérifiez ces problèmes de configuration courants.

<AccordionGroup>
  <Accordion title="Toutes mes pages OpenAPI sont entièrement vides">
    Dans ce cas, il est probable que Mintlify ne parvienne pas à trouver votre document OpenAPI,
    ou que votre document OpenAPI ne soit pas valide.

    L’exécution de `mint dev` en local devrait permettre de mettre en évidence certains de ces problèmes.

    Pour vérifier que votre document OpenAPI est valide :

    1. Accédez à [ce validateur](https://editor.swagger.io/)
    2. Ouvrez l’onglet &quot;Validate text&quot;
    3. Collez votre document OpenAPI
    4. Cliquez sur &quot;Validate it!&quot;

    Si la zone de texte qui apparaît ci-dessous a une bordure verte, votre document a bien passé la validation.
    C’est exactement le package de validation que Mintlify utilise pour valider les documents OpenAPI. Si votre document
    passe la validation ici, il y a de fortes chances que le problème vienne d’ailleurs.

    De plus, Mintlify ne prend pas en charge OpenAPI 2.0. Si votre document utilise cette version de la spécification,
    vous risquez de rencontrer ce problème. Vous pouvez convertir votre document sur [editor.swagger.io](https://editor.swagger.io/) (dans Edit &gt; Convert to OpenAPI 3) :

    <Frame>
      ![Capture d’écran de Swagger Editor avec le menu Edit ouvert et l’option "Convert to OpenAPI 3" mise en évidence.](/images/convert-oas-3.png)
    </Frame>
  </Accordion>

  <Accordion title="L’une de mes pages OpenAPI est complètement vide">
    Cela est généralement dû à une faute de frappe dans le champ `openapi` des métadonnées de la page. Assurez-vous
    que la méthode HTTP et le chemin correspondent exactement à ceux indiqués dans le document OpenAPI.

    Voici un exemple de ce qui peut se passer :

    ```mdx get-user.mdx
    ---
    openapi: "GET /users/{id}/"
    ---
    ```

    ```yaml openapi.yaml
    paths:
      "/users/{id}":
        get: ...
    ```

    Notez que le chemin indiqué dans le champ `openapi` se termine par une barre oblique, alors que ce n’est pas le cas du chemin dans le document OpenAPI.

    Un autre problème fréquent est une faute de frappe dans le nom du fichier. Si vous indiquez un document OpenAPI précis
    dans le champ `openapi`, assurez-vous que le nom du fichier est correct. Par exemple, si vous avez deux documents OpenAPI
    `openapi/v1.json` et `openapi/v2.json`, vos métadonnées peuvent ressembler à ceci :

    ```mdx api-reference/v1/users/get-user.mdx
    ---
    openapi: "v1 GET /users/{id}"
    ---
    ```
  </Accordion>

  <Accordion title="Les requêtes du bac à sable API ne fonctionnent pas">
    Si vous avez configuré un domaine personnalisé, le problème peut venir de votre proxy inverse. Par
    défaut, les requêtes effectuées via le bac à sable API commencent par une requête `POST` vers le
    chemin `/_mintlify/api/request` sur le site de documentation. Si vous configurez votre proxy inverse pour n’autoriser que les requêtes `GET`,
    toutes ces requêtes échoueront. Pour corriger le problème, configurez votre proxy inverse pour
    autoriser les requêtes `POST` vers le chemin `/_mintlify/api/request`.

    Sinon, si votre proxy inverse ne vous permet pas d’accepter les requêtes `POST`, vous pouvez configurer Mintlify pour envoyer les requêtes directement à votre backend à l’aide du paramètre `api.playground.proxy` dans `docs.json`, comme décrit dans la [documentation des paramètres](/fr/organize/settings-api). Avec cette configuration, vous devez configurer CORS sur votre serveur, car les requêtes proviennent directement du navigateur des utilisateurs au lieu de passer par votre proxy.
  </Accordion>

  <Accordion title="Les entrées de navigation OpenAPI ne génèrent pas de pages">
    Si vous utilisez une configuration de navigation OpenAPI, mais que les pages ne se génèrent pas, vérifiez les problèmes courants suivants :

    1. **Spécification OpenAPI par défaut manquante** : Assurez-vous qu’un champ `openapi` est défini pour l’élément de navigation :

    ```json {5}
    "navigation": {
      "groups": [
        {
          "group": "API reference",
          "openapi": "/path/to/openapi.json",
          "pages": [
            "GET /users",
            "POST /users"
          ]
        }
      ]
    }
    ```

    2. **Héritage de la spécification OpenAPI** : si vous utilisez une Navigation imbriquée, assurez-vous que les groupes enfants héritent de la bonne spécification OpenAPI ou définissez la leur.

    3. **Problèmes de validation** : utilisez `mint validate` pour vérifier que votre document OpenAPI est valide.
  </Accordion>

  <Accordion title="Certaines opérations OpenAPI apparaissent dans la navigation, mais pas les autres">
    1. **Opérations masquées** : Les opérations marquées par `x-hidden: true` dans votre spécification OpenAPI n’apparaîtront pas dans la navigation générée automatiquement.
    2. **Opérations non valides** : Les opérations comportant des erreurs de validation dans la spécification OpenAPI peuvent être ignorées. Vérifiez votre document OpenAPI pour détecter d’éventuelles erreurs de syntaxe.
    3. **Inclusion manuelle ou automatique** : Si vous faites référence à des points de terminaison d’une spécification OpenAPI, seules les opérations explicitement référencées apparaissent dans la navigation. Aucune autre page n’est ajoutée automatiquement. Cela inclut les opérations référencées dans les éléments de navigation enfants.
  </Accordion>

  <Accordion title="Navigation mixte (pages OpenAPI et MDX) ne fonctionne pas correctement">
    Lorsque vous combinez des opérations OpenAPI avec des pages de documentation classiques dans la Navigation :

    1. **Conflits de fichiers** : vous ne pouvez pas avoir à la fois un fichier `MDX` et une entrée de navigation pour la même opération. Par exemple, si vous avez `get-users.mdx`, n’incluez pas non plus `"GET /users"` dans votre navigation. Si vous avez besoin d’un fichier portant le même nom qu’une opération, utilisez l’extension `x-mint` pour le point de terminaison afin que le `href` renvoie vers un autre emplacement.
    2. **Résolution des chemins** : les entrées de navigation qui ne correspondent pas à des opérations OpenAPI sont traitées comme des chemins de fichier. Assurez-vous que vos fichiers `MDX` existent aux emplacements attendus.
    3. **Respect de la casse** : la correspondance des opérations OpenAPI est sensible à la casse. Assurez-vous que les méthodes HTTP sont en majuscules dans les entrées de navigation.
  </Accordion>
</AccordionGroup>
