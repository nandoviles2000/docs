Git vous permet de gérer et de suivre les modifications apportées aux fichiers. Git est le système de gestion de versions de référence pour les flux de travail de documentation as code, où vous gérez la documentation comme n’importe quelle autre base de code.

L’éditeur web s’occupe des opérations Git à votre place. Comprendre quelques concepts clés vous aide à tirer le meilleur parti de l’éditeur et à collaborer avec votre équipe.

<div id="what-git-does-for-your-docs">
  ## Ce que Git apporte à votre documentation
</div>

Git suit chaque modification apportée à votre documentation. Il enregistre ce qui a changé, qui a effectué la modification, quand elle a été faite et pourquoi. Cela signifie que vous pouvez :

* Consulter l’historique complet de n’importe quelle page.
* Annuler des modifications en revenant à une version précédente.
* Travailler sur des mises à jour sans affecter votre site en ligne.
* Vérifier les modifications avant leur mise en ligne.

Votre dépôt de documentation est l’ensemble des fichiers, ainsi que leur historique, qui composent votre site de documentation. L’éditeur web se connecte à ce dépôt pour lire et mettre à jour votre contenu.

<div id="key-concepts">
  ## Concepts clés
</div>

Voici les concepts Git que vous rencontrerez le plus souvent lorsque vous utilisez l’éditeur web.

<AccordionGroup>
  <Accordion title="Commit">
    Un instantané enregistré de vos modifications à un moment donné. Chaque commit inclut un message décrivant les changements et crée un enregistrement permanent dans l’historique de votre projet.

    Lorsque vous enregistrez des modifications, l’éditeur web crée un commit.
  </Accordion>

  <Accordion title="Branche">
    Une ligne de travail distincte dans votre dépôt. On parle aussi parfois de **branche de fonctionnalité**.

    Votre documentation publiée est générée à partir d’une **branche de déploiement**, généralement appelée `main`. Les autres branches vous permettent de travailler sur des modifications de manière indépendante. Les changements effectués sur une branche n’affectent pas votre site publié tant que vous ne les avez pas fusionnés dans votre branche de déploiement via une pull request (PR).

    Lorsque vous créez une branche, l’éditeur web crée une nouvelle branche dans votre dépôt. Vous pouvez rechercher des branches et passer de l’une à l’autre depuis le menu déroulant des branches dans la barre d’outils. Si vous avez des modifications non enregistrées, l’éditeur vous permet de les transférer vers la nouvelle branche ou de les laisser sur votre branche actuelle.
  </Accordion>

  <Accordion title="Branche de déploiement">
    La branche à partir de laquelle votre site de documentation publié est généré, généralement appelée `main`. Les modifications fusionnées dans cette branche sont automatiquement déployées sur votre site.
  </Accordion>

  <Accordion title="Pull request (PR)">
    Une proposition de fusion de modifications d’une branche vers une autre. Les pull requests (PR) permettent à votre équipe de relire et de discuter les changements avant leur mise en ligne.

    Lorsque vous publiez des modifications sur une branche de fonctionnalité, l’éditeur web crée une pull request (PR). Votre équipe examine et fusionne ensuite la pull request (PR) dans votre fournisseur Git (GitHub ou GitLab).
  </Accordion>

  <Accordion title="Fusion">
    L’action d’intégrer les modifications d’une branche dans une autre. Une fois qu’une pull request (PR) a été relue et approuvée par votre équipe, la fusion de la branche intègre vos modifications dans la branche de déploiement et les publie.
  </Accordion>

  <Accordion title="Conflit">
    Se produit lorsque deux personnes modifient différemment la même partie d’un fichier. L’éditeur vous aide à résoudre les conflits qui surviennent sur vos branches.
  </Accordion>

  <Accordion title="Diff">
    Comparaison qui montre les différences entre deux versions d’un fichier. Lors de la révision de pull requests (PR), les diffs mettent en évidence exactement ce qui a changé. L’éditeur web peut afficher les diffs de fichiers individuels lorsque vous examinez les modifications d’une branche avant de les publier.
  </Accordion>
</AccordionGroup>

<div id="how-the-editor-maps-to-git">
  ## Comment l’éditeur correspond à Git
</div>

Chaque action que vous effectuez dans l’éditeur web correspond à une opération Git.

| Votre action dans l’éditeur               | Opération Git en arrière-plan                                                                                                      |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Ouvrir un fichier                         | Récupérer la dernière version depuis votre dépôt                                                                                   |
| Enregistrer les modifications             | Créer un **commit**, un instantané de vos modifications dans l’historique du projet                                                |
| Créer une branche                         | Créer une **branche**, une ligne de travail distincte qui n’affecte pas votre site en ligne, sauf si vous choisissez de la publier |
| Publier sur votre branche de déploiement  | Envoyer directement votre commit, ce qui déclenche un déploiement                                                                  |
| Publier sur une branche de fonctionnalité | Créer une **pull request (PR)**, une proposition de fusion de vos modifications dans la branche de déploiement                     |
