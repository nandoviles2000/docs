La documentation commence à s&#39;éloigner du produit dès sa publication. Les fonctionnalités changent, les API évoluent et les éléments de l&#39;interface sont renommés. Sans maintenance intentionnelle, la documentation devient peu à peu un frein : les utilisateurs suivent des étapes obsolètes, rencontrent des erreurs et perdent confiance dans votre produit.

Ce guide explique comment intégrer la maintenance à votre flux de travail afin que votre documentation reste fiable sans nécessiter une mobilisation permanente de toute l&#39;équipe.

<div id="assign-ownership">
  ## Attribuer un responsable
</div>

Une documentation sans responsable n’est pas maintenue. Il faut que quelqu’un se sente responsable de chaque section de votre documentation pour que les problèmes soient réellement corrigés.

Avoir un responsable ne veut pas forcément dire qu’une seule personne rédige tout. Cela signifie que quelqu’un répond de l’exactitude du contenu. Modèles de responsabilité courants :

* **Centralisé :** Une équipe de documentation ou un rédacteur technique est responsable de l’ensemble du contenu. Ce modèle fonctionne bien pour les petites équipes et les produits pour lesquels l’équipe documentation dispose de suffisamment de contexte pour tout maintenir.
* **Distribué :** Les responsables produit, les responsables techniques ou les chefs d’équipe gèrent la documentation de leurs domaines. Ce modèle fonctionne bien pour les produits plus vastes avec des domaines spécialisés. Il nécessite un coordinateur pour garantir la cohérence et repérer les lacunes.
* **Hybride :** Une équipe documentation prend en charge le contenu principal (prise en main, navigation, style), tandis que les équipes métier gèrent la référence technique et les guides de leurs fonctionnalités.

Quel que soit le modèle que vous utilisez, rendez cette responsabilité visible — dans les fichiers eux-mêmes, dans une feuille de calcul partagée ou dans votre outil de gestion de projet.

<div id="build-a-review-cadence">
  ## Définir un rythme de révision
</div>

Des révisions régulières permettent de détecter les problèmes avant qu’ils n’affectent les utilisateurs. Le bon rythme dépend de la vitesse à laquelle votre produit évolue.

<div id="trigger-based-reviews">
  ### Revues déclenchées par les changements
</div>

L’approche la plus fiable consiste à revoir la documentation chaque fois que le produit évolue :

* Mettre à jour la documentation dans la même pull request (PR) que la modification du code
* Inclure une vérification de la documentation dans votre liste de contrôle de lancement de fonctionnalité
* Exiger une validation de la documentation avant de clôturer tout ticket qui modifie un comportement visible par les utilisateurs

C’est plus viable que des revues planifiées, car la mise à jour de la documentation intervient alors que le changement est encore bien présent dans l’esprit de l’ingénieur ou du chef de produit.

<div id="scheduled-reviews">
  ### Revues planifiées
</div>

Pour le contenu qui n&#39;est lié à aucune fonctionnalité spécifique, les revues planifiées permettent de repérer la dérive qui s&#39;accumule :

* **Chaque mois :** Passez en revue les pages à fort trafic pour vérifier leur exactitude. Comme elles touchent le plus grand nombre d&#39;utilisateurs, elles méritent une attention plus fréquente.
* **Chaque trimestre :** Auditez les pages signalées par de faibles scores de retour ou une forte corrélation avec les tickets de support.
* **Chaque année :** Audit complet du contenu — recherchez les exemples obsolètes, les approches remplacées et le contenu qui ne reflète plus l&#39;état actuel du produit.

<div id="use-automation-to-surface-stale-content">
  ### Utilisez l’automatisation pour repérer le contenu obsolète
</div>

Le suivi manuel des dates de révision sur des centaines de pages n’est pas viable à grande échelle. Automatisez tout ce que vous pouvez :

* Signalez pour révision les pages qui n’ont pas été mises à jour depuis plus de 90 jours
* Surveillez les analyses de la recherche pour repérer les requêtes qui ne renvoient aucun résultat : elles indiquent souvent qu’un contenu devrait exister, mais n’existe pas
* Utilisez les [vérifications CI](/fr/deploy/ci) pour appliquer les exigences relatives aux métadonnées d’en-tête et détecter les liens rompus à chaque pull request (PR)

<Tip>
  Utilisez les [flux de travail](/fr/agent/workflows) pour exécuter des vérifications de maintenance automatisées à intervalles réguliers : signaler le contenu obsolète, vérifier les métadonnées manquantes ou mettre en évidence les pages qui reçoivent régulièrement de faibles scores de satisfaction.
</Tip>

<div id="automate-what-you-can">
  ## Automatisez ce que vous pouvez
</div>

L’automatisation ne peut pas remplacer le jugement éditorial, mais elle réduit le travail manuel nécessaire pour repérer les problèmes courants.

* **Liens rompus :** Exécutez `mint broken-links` avant la publication pour repérer les liens internes et externes rompus avant que les utilisateurs ne tombent dessus.
* **Respect du guide de style :** Un linter comme [Vale](https://vale.sh) vérifie vos textes à l’aide de règles configurables — cohérence terminologique, voix passive, ponctuation manquante — sur chaque pull request (PR). Consultez [Style et ton](/fr/guides/style-and-tone) pour en savoir plus sur le linting.
* **Mises à jour de la référence de l’API :** Si votre référence de l’API est générée à partir d’une spécification OpenAPI, automatisez la génération de la spécification dans votre pipeline de publication afin qu’elle ne prenne jamais de retard.
* **Brouillons de documentation automatisés :** Utilisez l’[API d’agent](/fr/guides/automate-agent) pour générer automatiquement des brouillons de documentation lorsque du code est fusionné.

<div id="know-when-to-rewrite">
  ## Sachez quand réécrire
</div>

Les corrections incrémentales ne suffisent pas toujours. Lorsqu&#39;une page a accumulé trop de mises en garde, de solutions de contournement et de contradictions, la modifier devient plus difficile que de repartir de zéro.

Voici les signes qu&#39;une page doit être réécrite plutôt que simplement modifiée :

* Les utilisateurs disent régulièrement ne pas comprendre, malgré plusieurs séries de modifications
* La page s&#39;est étoffée au point de couvrir plusieurs sujets distincts qui devraient faire l&#39;objet de pages séparées
* Le produit a tellement changé que la structure de la page ne reflète plus le fonctionnement de la fonctionnalité
* Plus de la moitié du contenu est constituée de cas particuliers, de mises en garde ou de « cela ne s&#39;applique pas si... »

Une réécriture paraît moins intimidante si vous commencez par un audit structuré : notez ce qui manque, ce qui est trompeur et ce qui est redondant avant d&#39;écrire quoi que ce soit. Effectuez les réécritures complètes par sprints ciblés, au lieu d&#39;essayer de tout faire d&#39;un coup.

<div id="remove-what-no-longer-belongs">
  ## Supprimez ce qui n’a plus lieu d’être
</div>

Une documentation erronée vaut pire que pas de documentation du tout. Les utilisateurs qui suivent des instructions inexactes perdent du temps et cessent d’avoir confiance en votre produit et en votre équipe. Lorsqu’un contenu est totalement inexact et ne peut pas être corrigé immédiatement, mieux vaut le supprimer que le laisser en ligne.

Lorsque vous supprimez du contenu :

* Mettez en place une redirection de l’ancienne URL vers la page actuelle la plus pertinente
* Vérifiez les liens internes qui pointent vers la page supprimée et mettez-les à jour
* Demandez-vous s’il est pertinent d’ajouter une brève note au journal des modifications si la page était largement utilisée

<div id="frequently-asked-questions">
  ## Questions fréquentes
</div>

<AccordionGroup>
  <Accordion title="Comment faire en sorte que les ingénieurs mettent à jour la documentation lorsqu'ils livrent des fonctionnalités ?">
    Faites-en une étape obligatoire, pas une simple demande. Intégrez la documentation à votre « definition of done » pour les fonctionnalités. Incluez les mises à jour de la documentation dans la même pull request (PR) que les modifications de code : le contexte reste ainsi frais et la relecture conjointe est plus facile. Quand les ingénieurs comprennent qu&#39;une documentation obsolète génère des tickets de support qui leur reviennent, la nécessité de la maintenir devient plus évidente.
  </Accordion>

  <Accordion title="Comment gérer la documentation des fonctionnalités dépréciées ?">
    Laissez la documentation des fonctionnalités dépréciées accessible, mais signalez-la clairement. Ajoutez un avis en haut de la page indiquant que la fonctionnalité est dépréciée, quand elle sera supprimée et vers quoi les utilisateurs doivent migrer. Ne supprimez pas la page tant que la fonctionnalité n&#39;a pas réellement été retirée : les utilisateurs sur d&#39;anciennes versions en ont encore besoin. Une fois la fonctionnalité supprimée, redirigez l&#39;URL vers le guide de migration ou vers la documentation de la fonctionnalité de remplacement.
  </Accordion>

  <Accordion title="Quel est le processus de maintenance minimum viable pour une petite équipe ?">
    Deux pratiques couvrent l&#39;essentiel : mettez à jour la documentation dans la même PR que les modifications de code, et exécutez `mint broken-links` avant chaque publication. Ces deux habitudes évitent les formes de dérive les plus courantes — instructions obsolètes et liens morts — sans nécessiter d&#39;infrastructure documentaire dédiée. Ajoutez ensuite des revues régulières et de l&#39;automatisation à mesure que l&#39;équipe et le produit grandissent.
  </Accordion>

  <Accordion title="Comment prioriser la dette documentaire ?">
    Par impact. Une page obsolète avec 5 000 vues mensuelles et de faibles scores de satisfaction est plus urgente qu&#39;une page dépassée que personne ne lit. Utilisez les analyses pour classer le contenu par trafic, recoupez avec les scores de retour et corrélez avec le volume des tickets de support afin d&#39;établir une liste de priorités. Corrigez les pages que les utilisateurs consultent réellement, pas celles qui paraissent désordonnées à l&#39;équipe.
  </Accordion>
</AccordionGroup>
