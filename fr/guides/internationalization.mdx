L’internationalisation (i18n) consiste à concevoir des logiciels ou du contenu pour qu’ils fonctionnent dans différentes langues et différents paramètres régionaux. Ce guide explique comment structurer les fichiers, configurer la navigation et gérer efficacement les traductions afin d’aider les utilisateurs à accéder à votre documentation dans la langue de leur choix et d’élargir votre portée à l’international.

<div id="file-structure">
  ## Structure des fichiers
</div>

Organisez le contenu traduit dans des répertoires propres à chaque langue afin de faciliter la maintenance de votre documentation et de structurer votre Navigation par langue.

Créez un répertoire distinct pour chaque langue à l’aide des [codes de langue ISO 639-1](https://en.wikipedia.org/wiki/List_of_ISO_639-1_codes). Placez les fichiers traduits dans ces répertoires en conservant la même structure que pour votre langue par défaut.

<Expandable title="codes de langue pris en charge">
  * `ar` - Arabe
  * `ca` - Catalan
  * `cs` - Tchèque
  * `zh` ou `zh-Hans` - Chinois (simplifié)
  * `zh-Hant` - Chinois (traditionnel)
  * `de` - Allemand
  * `en` - Anglais
  * `es` - Espagnol
  * `fi` - Finnois
  * `fr` - Français
  * `fr-CA` - Français (canadien)
  * `he` - Hébreu
  * `hi` - Hindi
  * `hu` - Hongrois
  * `id` - Indonésien
  * `it` - Italien
  * `ja` - Japonais
  * `ko` - Coréen
  * `lv` - Letton
  * `nl` - Néerlandais
  * `no` - Norvégien
  * `pl` - Polonais
  * `pt` ou `pt-BR` - Portugais
  * `ro` - Roumain
  * `ru` - Russe
  * `sv` - Suédois
  * `tr` - Turc
  * `uk` - Ukrainien
  * `uz` - Ouzbek
  * `vi` - Vietnamien
</Expandable>

```text Example file structure
docs/
├── index.mdx                    # Anglais (par défaut)
├── quickstart.mdx
├── fr/
│   ├── index.mdx               # Français
│   ├── quickstart.mdx
├── es/
│   ├── index.mdx               # Espagnol
│   ├── quickstart.mdx
└── zh/
    ├── index.mdx               # Chinois
    └── quickstart.mdx
```

<Tip>
  Conservez les mêmes noms de fichiers et la même arborescence dans toutes les langues. Cela facilite la maintenance des traductions et l’identification des contenus manquants.
</Tip>

<div id="configure-the-language-switcher">
  ## Configurer le sélecteur de langue
</div>

Pour ajouter un sélecteur de langue à votre documentation, configurez le tableau `languages` dans la section Navigation de votre `docs.json`.

```json docs.json
{
  "navigation": {
    "languages": [
      {
        "language": "en",
        "groups": [
          {
            "group": "Getting started",
            "pages": ["index", "quickstart"]
          }
        ]
      },
      {
        "language": "es",
        "groups": [
          {
            "group": "Comenzando",
            "pages": ["es/index", "es/quickstart"]
          }
        ]
      }
    ]
  }
}
```

Chaque entrée de langue du tableau `languages` nécessite :

* `language` : code de langue ISO 639-1
* Structure de navigation complète
* Chemins vers les fichiers traduits

La structure de navigation peut varier d’une langue à l’autre afin de répondre aux besoins de contenu propres à chaque langue.

<Warning>
  N’utilisez pas le même chemin de page dans plusieurs langues. La duplication de chemins entre les langues entraîne un comportement indéfini. Chaque chemin de page ne doit apparaître que dans la navigation d’une seule langue.
</Warning>

<div id="set-default-language">
  ### Définir la langue par défaut
</div>

La première langue du tableau `languages` est utilisée automatiquement comme langue par défaut. Pour en définir une autre, réorganisez le tableau ou ajoutez la propriété `default` :

```json docs.json
{
  "navigation": {
    "languages": [
      {
        "language": "es",
        "groups": [...]
      },
      {
        "language": "en",
        "groups": [...]
      }
    ]
  }
}
```

Sinon, utilisez la propriété `default` pour modifier l’ordre :

```json docs.json
{
  "navigation": {
    "languages": [
      {
        "language": "en",
        "groups": [...]
      },
      {
        "language": "es",
        "default": true,
        "groups": [...]
      }
    ]
  }
}
```

<div id="single-language-documentation">
  ### Documentation dans une seule langue
</div>

Si vous souhaitez proposer une seule langue sans sélecteur de langue, supprimez le champ `languages` de votre configuration de navigation. Définissez ensuite directement votre structure de navigation :

```json docs.json
{
  "navigation": {
    "tabs": [
      {
        "tab": "Documentation",
        "groups": [
          {
            "group": "Getting started",
            "pages": ["index", "quickstart"]
          }
        ]
      }
    ]
  }
}
```

Cela affiche votre documentation dans une seule langue, sans le sélecteur de langue.

<Tip>
  Traduisez les libellés de Navigation, comme les noms de groupes ou d’onglets, pour qu’ils correspondent à la langue du contenu. Vous offrez ainsi une expérience entièrement localisée à vos utilisateurs.
</Tip>

<div id="global-navigation">
  ### Navigation globale
</div>

Pour ajouter des éléments de Navigation globaux visibles dans toutes les langues, configurez l&#39;objet `global` dans la section Navigation de votre `docs.json`.

```json docs.json
{
  "navigation": {
    "global": {
      "anchors": [
        {
          "anchor": "Documentation",
          "href": "https://example.com/docs"
        },
        {
          "anchor": "Blog",
          "href": "https://example.com/blog"
        }
      ]
    },
    "languages": [
      // Navigation spécifique à la langue
    ]
  }
}
```

<div id="localized-footer-and-navbar">
  ### Pied de page et barre de navigation localisés
</div>

Personnalisez le pied de page et la barre de navigation pour chaque langue afin d’afficher du contenu traduit et des liens propres à chaque région.

Ajoutez les propriétés `footer` et `navbar` à la configuration de chaque langue :

```json docs.json
{
  "navigation": {
    "languages": [
      {
        "language": "en",
        "footer": {
          "socials": {
            "x": "https://x.com/mintlify"
          },
          "links": [
            {
              "header": "Resources",
              "items": [
                { "label": "Documentation", "href": "/en/docs" },
                { "label": "Blog", "href": "https://mintlify.com/blog" }
              ]
            }
          ]
        },
        "navbar": {
          "links": [
            { "label": "Docs", "href": "/en/docs" }
          ],
          "primary": {
            "type": "button",
            "label": "Get Started",
            "href": "/en/quickstart"
          }
        },
        "groups": [
          {
            "group": "Getting started",
            "pages": ["en/quickstart", "en/index"]
          }
        ]
      },
      {
        "language": "es",
        "footer": {
          "socials": {
            "x": "https://x.com/mintlify"
          },
          "links": [
            {
              "header": "Recursos",
              "items": [
                { "label": "Documentación", "href": "/es/docs" },
                { "label": "Blog", "href": "https://mintlify.com/blog" }
              ]
            }
          ]
        },
        "navbar": {
          "links": [
            { "label": "Documentación", "href": "/es/docs" }
          ],
          "primary": {
            "type": "button",
            "label": "Comenzar",
            "href": "/es/quickstart"
          }
        },
        "groups": [
          {
            "group": "Comenzando",
            "pages": ["es/quickstart", "es/index"]
          }
        ]
      }
    ]
  }
}
```

Les `footer` et `navbar` propres à la langue remplacent les paramètres globaux pour cette langue. Si une langue ne définit pas ces propriétés, elle hérite de la configuration globale.

Vous pouvez également configurer un `banner` propre à une langue en suivant le même principe.

<div id="translation-workflow">
  ### Workflow de traduction
</div>

1. Mettez à jour le contenu source dans votre langue principale.
2. Identifiez le contenu modifié.
3. Traduisez le contenu modifié.
4. Vérifiez l’exactitude des traductions.
5. Mettez à jour les fichiers traduits.
6. Vérifiez que la Navigation et les liens fonctionnent.

<div id="external-translation-providers">
  ### Fournisseurs de traduction externes
</div>

Si vous travaillez avec vos propres prestataires de traduction ou traducteurs régionaux, vous pouvez intégrer leur workflow à votre documentation Mintlify à l’aide de GitHub Actions ou d’outils CI/CD similaires.

1. **Exporter le contenu source** : extrayez les fichiers MDX à traduire.
2. **Envoyer aux traducteurs** : transmettez les fichiers à votre prestataire de traduction.
3. **Recevoir les traductions** : récupérez les fichiers MDX traduits.
4. **Importer et déployer** : ajoutez les fichiers traduits aux répertoires de langue et mettez à jour la Navigation.

Ce workflow GitHub Actions exporte automatiquement le contenu anglais modifié à traduire lorsque des PR sont fusionnées dans `main`.

```yaml .github/workflows/export-for-translation.yml
name: Export content for translation

on:
  push:
    branches: [main]
    paths:
      - '*.mdx'
      - '!es/**'
      - '!fr/**'
      - '!zh/**'

# Empêcher les exécutions simultanées du workflow pour éviter les conditions de concurrence
concurrency:
  group: translation-export-${{ github.ref }}
  cancel-in-progress: false

jobs:
  export:
    runs-on: ubuntu-latest
    
    # Sortie anticipée si aucun changement détecté (optionnel - sécurité supplémentaire)
    outputs:
      files-changed: ${{ steps.changed.outputs.has-files }}
    
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
        with:
          fetch-depth: 2

      - name: Get changed MDX files
        id: changed
        run: |
          # Vérifier si le commit parent existe (gère le push initial)
          if ! git rev-parse HEAD~1 >/dev/null 2>&1; then
            echo "has-files=false" >> $GITHUB_OUTPUT
            echo "files=" >> $GITHUB_OUTPUT
            echo "No parent commit found - skipping export"
            exit 0
          fi
          
          # Récupérer la liste des fichiers MDX modifiés (en excluant les répertoires de traduction)
          files=$(git diff --name-only HEAD~1 HEAD -- '*.mdx' ':!es/' ':!fr/' ':!zh/' | tr '\n' ' ')
          
          if [ -z "$files" ]; then
            echo "has-files=false" >> $GITHUB_OUTPUT
            echo "files=" >> $GITHUB_OUTPUT
            echo "No MDX files changed - skipping export"
          else
            echo "has-files=true" >> $GITHUB_OUTPUT
            echo "files=$files" >> $GITHUB_OUTPUT
            echo "Found changed files: $files"
          fi
        shell: bash

      - name: Create translation package directory
        if: steps.changed.outputs.has-files == 'true'
        run: |
          mkdir -p translation-export
          echo "Created translation-export directory"

      - name: Copy changed files to export directory
        if: steps.changed.outputs.has-files == 'true'
        run: |
          failed_count=0
          for file in ${{ steps.changed.outputs.files }}; do
            if [ -f "$file" ]; then
              target_dir="translation-export/$(dirname "$file")"
              mkdir -p "$target_dir"
              cp "$file" "$target_dir/"
              echo "✓ Copied: $file"
            else
              echo "✗ File not found: $file"
              ((failed_count++))
            fi
          done
          
          if [ $failed_count -gt 0 ]; then
            echo "Warning: $failed_count file(s) could not be copied"
          fi
        shell: bash

      - name: Validate translation package
        if: steps.changed.outputs.has-files == 'true'
        run: |
          echo "Translation package contents:"
          find translation-export -type f -name "*.mdx" | sort
          echo ""
          file_count=$(find translation-export -type f -name "*.mdx" | wc -l)
          echo "Total MDX files: $file_count"

      - name: Upload translation package
        if: steps.changed.outputs.has-files == 'true'
        uses: actions/upload-artifact@v4
        with:
          name: translation-export-${{ github.sha }}
          path: translation-export/
          retention-days: 30
          if-no-files-found: error
          compression-level: 9

      - name: Print job summary
        if: steps.changed.outputs.has-files == 'true'
        run: |
          echo "## Translation Export Complete" >> $GITHUB_STEP_SUMMARY
          echo "" >> $GITHUB_STEP_SUMMARY
          echo "**Artifact:** \`translation-export-${{ github.sha }}\`" >> $GITHUB_STEP_SUMMARY
          echo "" >> $GITHUB_STEP_SUMMARY
          echo "**Changed Files:**" >> $GITHUB_STEP_SUMMARY
          echo "${{ steps.changed.outputs.files }}" | tr ' ' '\n' | sed 's/^/- /' >> $GITHUB_STEP_SUMMARY
```

Ce workflow GitHub Actions valide et importe le contenu traduit lorsqu’il est ajouté via une PR.

```yaml .github/workflows/import-translations.yml
name: Import translations

on:
  pull_request:
    paths:
      - 'es/**'
      - 'fr/**'
      - 'zh/**'

# Définir les permissions explicites
permissions:
  contents: read
  pull-requests: write

jobs:
  validate:
    runs-on: ubuntu-latest
    
    outputs:
      validation-status: ${{ steps.final-check.outputs.status }}
    
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
        with:
          fetch-depth: 0  # Full history to ensure origin/main is available

      - name: Fetch origin/main reference
        run: |
          git fetch origin main:origin/main 2>/dev/null || echo "origin/main not available, using latest"
        continue-on-error: true

      - name: Get changed translation files
        id: changed-files
        run: |
          # Récupérer tous les fichiers MDX modifiés dans les répertoires de traduction
          files=$(git diff --name-only origin/main..HEAD -- 'es/**/*.mdx' 'fr/**/*.mdx' 'zh/**/*.mdx' | sort)
          
          if [ -z "$files" ]; then
            echo "No translation MDX files detected in this PR"
            echo "files=" >> $GITHUB_OUTPUT
            echo "count=0" >> $GITHUB_OUTPUT
          else
            echo "Found $(echo "$files" | wc -l) translation files"
            echo "$files"
            echo "files=$files" >> $GITHUB_OUTPUT
            echo "count=$(echo "$files" | wc -l)" >> $GITHUB_OUTPUT
          fi
        shell: bash

      - name: Validate frontmatter
        id: frontmatter
        if: steps.changed-files.outputs.count > 0
        run: |
          failed_files=()
          success_count=0
          total=${{ steps.changed-files.outputs.count }}
          
          while IFS= read -r file; do
            if [ ! -f "$file" ]; then
              echo "✗ File not found: $file"
              failed_files+=("$file")
              continue
            fi
            
            # Vérifier la validité des métadonnées d'en-tête (les lignes 1-2 doivent être ---)
            first_line=$(sed -n '1p' "$file")
            second_line=$(sed -n '2p' "$file")
            last_line=$(awk 'NF' "$file" | tail -1)
            
            if [ "$first_line" = "---" ] && grep -q "^---$" "$file"; then
              echo "✓ Valid frontmatter: $file"
              ((success_count++))
            else
              echo "✗ Invalid frontmatter in $file"
              echo "  Line 1: '$first_line'"
              failed_files+=("$file")
            fi
          done <<< "${{ steps.changed-files.outputs.files }}"
          
          echo ""
          echo "Frontmatter check: $success_count/$total passed"
          
          if [ ${#failed_files[@]} -gt 0 ]; then
            echo "frontmatter_valid=false" >> $GITHUB_OUTPUT
            printf 'failed_files=%s\n' "${failed_files[@]}" >> $GITHUB_OUTPUT
          else
            echo "frontmatter_valid=true" >> $GITHUB_OUTPUT
          fi
        shell: bash

      - name: Check file structure
        id: structure
        if: steps.changed-files.outputs.count > 0
        run: |
          missing_sources=()
          orphaned_count=0
          
          while IFS= read -r translated_file; do
            # Extraire la langue et le chemin relatif
            # ex. : "es/docs/guide.mdx" -> lang="es", relative_path="docs/guide.mdx"
            lang=$(echo "$translated_file" | cut -d'/' -f1)
            relative_path=$(echo "$translated_file" | cut -d'/' -f2-)
            source_file="$relative_path"
            
            if [ ! -f "$source_file" ]; then
              echo "Missing source: $translated_file -> $source_file"
              missing_sources+=("$translated_file")
              ((orphaned_count++))
            else
              echo "✓ Found source: $translated_file -> $source_file"
            fi
          done <<< "${{ steps.changed-files.outputs.files }}"
          
          echo ""
          echo "Structure check: $orphaned_count orphaned file(s)"
          
          if [ $orphaned_count -gt 0 ]; then
            echo "structure_valid=false" >> $GITHUB_OUTPUT
            printf 'missing_sources=%s\n' "${missing_sources[@]}" >> $GITHUB_OUTPUT
          else
            echo "structure_valid=true" >> $GITHUB_OUTPUT
          fi
        shell: bash

      - name: Validate file integrity
        id: integrity
        if: steps.changed-files.outputs.count > 0
        run: |
          integrity_passed=true
          
          while IFS= read -r file; do
            # Vérifier que le fichier est lisible et non vide
            if [ ! -r "$file" ] || [ ! -s "$file" ]; then
              echo "✗ File integrity issue: $file (not readable or empty)"
              integrity_passed=false
            fi
            
            # Vérification de base : le fichier doit avoir du contenu après les métadonnées d'en-tête
            line_count=$(wc -l < "$file")
            if [ "$line_count" -lt 5 ]; then
              echo "File is suspiciously short: $file ($line_count lines)"
            fi
          done <<< "${{ steps.changed-files.outputs.files }}"
          
          if [ "$integrity_passed" = true ]; then
            echo "integrity_valid=true" >> $GITHUB_OUTPUT
          else
            echo "integrity_valid=false" >> $GITHUB_OUTPUT
          fi
        shell: bash

      - name: Generate validation report
        if: always()
        run: |
          echo "## Translation Validation Report" >> $GITHUB_STEP_SUMMARY
          echo "" >> $GITHUB_STEP_SUMMARY
          echo "**Files Changed:** ${{ steps.changed-files.outputs.count }}" >> $GITHUB_STEP_SUMMARY
          echo "" >> $GITHUB_STEP_SUMMARY
          
          if [ "${{ steps.changed-files.outputs.count }}" = "0" ]; then
            echo "No translation MDX files found in this PR" >> $GITHUB_STEP_SUMMARY
            echo "" >> $GITHUB_STEP_SUMMARY
            echo "> This could mean:" >> $GITHUB_STEP_SUMMARY
            echo "- Only non-MDX files in es/, fr/, or zh/ directories were changed" >> $GITHUB_STEP_SUMMARY
            echo "- Workflow was triggered but no translation content to validate" >> $GITHUB_STEP_SUMMARY
          else
            echo "### Validation Results" >> $GITHUB_STEP_SUMMARY
            echo "- Frontmatter: ${{ steps.frontmatter.outputs.frontmatter_valid }}" >> $GITHUB_STEP_SUMMARY
            echo "- File Structure: ${{ steps.structure.outputs.structure_valid }}" >> $GITHUB_STEP_SUMMARY
            echo "- File Integrity: ${{ steps.integrity.outputs.integrity_valid }}" >> $GITHUB_STEP_SUMMARY
            echo "" >> $GITHUB_STEP_SUMMARY
          fi
        shell: bash

      - name: Final validation check
        id: final-check
        # N'exécuter cette vérification que s'il y avait effectivement des fichiers MDX à valider
        if: steps.changed-files.outputs.count > 0
        run: |
          validation_failed=false
          
          if [ "${{ steps.frontmatter.outputs.frontmatter_valid }}" != "true" ]; then
            echo "Frontmatter validation failed"
            validation_failed=true
          fi
          
          if [ "${{ steps.structure.outputs.structure_valid }}" != "true" ]; then
            echo "File structure validation failed"
            validation_failed=true
          fi
          
          if [ "${{ steps.integrity.outputs.integrity_valid }}" != "true" ]; then
            echo "File integrity validation failed"
            validation_failed=true
          fi
          
          if [ "$validation_failed" = true ]; then
            echo "status=failed" >> $GITHUB_OUTPUT
            exit 1
          else
            echo "status=passed" >> $GITHUB_OUTPUT
            echo "All validations passed"
          fi
        shell: bash

      - name: Handle no-files-to-validate case
        # S'exécuter uniquement lorsqu'il n'y a aucun fichier MDX à valider
        if: steps.changed-files.outputs.count == 0
        run: |
          echo "No translation MDX files to validate - PR is valid"
          echo "status=no-changes" >> ${{ steps.final-check.outputs }}
        shell: bash
```

**Bonnes pratiques pour les flux de travail de traduction externes**

* **Préserver les métadonnées d’en-tête** : veillez à ce que les traducteurs conservent intactes les métadonnées d’en-tête YAML et ne traduisent que les valeurs de `title` et `description`.
* **Protéger les blocs de code** : indiquez à vos prestataires que les blocs de code ne doivent pas être traduits.
* **Utiliser une mémoire de traduction** : fournissez des glossaires avec les termes techniques qui doivent rester en anglais ou suivre des traductions spécifiques.
* **Automatiser la validation** : utilisez des contrôles CI pour vérifier la syntaxe MDX et les métadonnées d’en-tête avant de fusionner les traductions.
* **Contrôle de version** : suivez la version source de chaque traduction afin de repérer les contenus obsolètes.

  ## Bonnes pratiques

<div id="date-and-number-formats">
  ### Formats de dates et de nombres
</div>

Tenez compte des conventions locales de formatage des dates et des nombres.

* Formats de date : MM/DD/YYYY (mois/jour/année) ou DD/MM/YYYY (jour/mois/année)
* Formats de nombre : 1,000.00 ou 1.000,00
* Symboles monétaires : $100.00 ou 100,00€

Incluez des exemples au format approprié pour chaque langue, ou utilisez des formats universellement compris.

<div id="maintain-consistency">
  ### Maintenez la cohérence
</div>

* Assurez une parité de contenu dans toutes les langues afin que chaque utilisateur bénéficie du même niveau d’information.
* Créez un glossaire de traduction pour les termes techniques.
* Conservez la même structure de contenu dans toutes les langues.
* Veillez à reprendre le ton et le style de votre contenu source.
* Utilisez des branches Git pour gérer le travail de traduction séparément des mises à jour du contenu principal.

<div id="layout-differences">
  ### Différences de mise en page
</div>

Certaines langues nécessitent plus ou moins d’espace que l’anglais. Testez votre contenu traduit sur différentes tailles d’écran afin de vérifier que :

* La navigation s’affiche correctement.
* Les blocs de code ne débordent pas.
* Les tableaux et les autres textes mis en forme restent lisibles.
* Les images se redimensionnent correctement.

<div id="character-encoding">
  ### Encodage des caractères
</div>

Assurez-vous que votre environnement de développement et votre pipeline de déploiement prennent en charge l’encodage UTF-8 afin d’afficher correctement tous les caractères des langues utilisant des alphabets différents et des caractères spéciaux.

<div id="frequently-asked-questions">
  ## Questions fréquentes
</div>

<AccordionGroup>
  <Accordion title="Dois-je traduire chaque page avant de lancer une nouvelle langue ?">
    Non. Vous pouvez lancer une langue avec une couverture partielle, puis l’étendre au fil du temps. Une approche courante consiste à traduire d’abord vos pages les plus consultées — généralement le contenu de prise en main, l’authentification et les principaux guides pratiques — et à laisser le contenu de référence moins consulté dans la langue par défaut jusqu’à ce que les traductions soient prêtes. Les utilisateurs préfèrent généralement avoir un peu de contenu traduit plutôt que rien du tout.
  </Accordion>

  <Accordion title="Que se passe-t-il lorsqu’une page traduite manque ?">
    Si un utilisateur accède à une URL traduite qui n’existe pas, il verra une 404. Pour éviter cela, soit n’incluez que les pages traduites dans votre Navigation propre à la langue, soit maintenez la parité entre votre langue par défaut et le contenu traduit. Utiliser la même structure de fichiers dans toutes les langues permet d’identifier facilement les traductions manquantes.
  </Accordion>

  <Accordion title="Les libellés de navigation doivent-ils être traduits ?">
    Oui. Les libellés de navigation — noms de groupes, titres d’onglets, texte des ancres — doivent correspondre à la langue du contenu. Un libellé anglais « Getting started » dans une section de documentation en espagnol crée une expérience déstabilisante. Mintlify prend en charge des structures de navigation propres à chaque langue, afin que chacune puisse avoir des libellés entièrement traduits.
  </Accordion>

  <Accordion title="Comment gérer les exemples de code dans du contenu traduit ?">
    Le code lui-même ne doit pas être traduit — les noms de variables, les appels de fonction et la syntaxe sont indépendants de la langue. Les commentaires dans les blocs de code peuvent être traduits s’ils expliquent des concepts que les utilisateurs doivent comprendre. Les instructions autour des blocs de code doivent être entièrement traduites.
  </Accordion>

  <Accordion title="Mintlify prend-il en charge les langues qui s’écrivent de droite à gauche, comme l’arabe ou l’hébreu ?">
    Oui. L’arabe (`ar`) et l’hébreu (`he`) figurent dans la liste des codes de langue pris en charge. Mintlify gère automatiquement la mise en page RTL lorsque ces codes de langue sont configurés. Testez votre documentation en RTL pour vérifier que la navigation, les tableaux et les blocs de code s’affichent correctement.
  </Accordion>
</AccordionGroup>
