Git est un système de contrôle de version qui suit les modifications apportées à votre documentation et facilite la collaboration au sein de l&#39;équipe. Avec Git, vous pouvez voir ce qui a changé au fil du temps dans les fichiers, qui a apporté ces modifications, quand et pourquoi. Git permet également de rétablir facilement des versions antérieures des fichiers si vous devez annuler des modifications.

L&#39;éditeur web effectue les opérations Git en arrière-plan. En comprenant Git, vous pouvez travailler plus efficacement avec l&#39;éditeur web et collaborer avec les membres de l&#39;équipe qui travaillent en local.

<div id="why-git-for-documentation">
  ## Pourquoi utiliser Git pour la documentation ?
</div>

Git offre des fonctionnalités essentielles pour gérer la documentation.

* **Historique des versions** : voyez ce qui a changé, quand et pourquoi, pour chaque fichier.
* **Collaboration** : plusieurs personnes peuvent travailler en même temps sur différentes parties.
* **Sécurité** : expérimentez sans risquer de perturber la documentation en ligne.
* **Flux de travail de révision** : les membres de l’équipe peuvent examiner les modifications avant leur publication.
* **Récupération** : corrigez des erreurs ou restaurez des versions précédentes.

<div id="new-to-git">
  ## Vous débutez avec Git ?
</div>

Si vous découvrez complètement Git et la gestion de versions, voici comment démarrer.

<Steps>
  <Step title="Commencez par utiliser l'éditeur web.">
    L&#39;[éditeur web](/fr/editor/index) gère automatiquement les opérations Git.

    * Visualisez les modifications au fur et à mesure.
    * Créez des branches en un clic.
    * Publiez et créez des pull requests (PR) sans utiliser de commandes Git.

    Cela vous permet d&#39;apprendre les concepts de Git sans passer par la ligne de commande.
  </Step>

  <Step title="Apprenez en pratiquant.">
    Quand vous utilisez l&#39;éditeur web, vous utilisez Git.

    * **Save changes** crée un commit.
    * **Create branch** crée une branche Git.
    * **Publish** ouvre une pull request (PR) pour revue.
  </Step>

  <Step title="Explorez le développement local quand c'est utile.">
    Vous pouvez gérer toute votre documentation avec l&#39;éditeur web et le tableau de bord, mais vous pouvez adapter votre flux de travail en travaillant dans votre environnement local.

    * Créez et modifiez des fichiers dans votre éditeur préféré.
    * Utilisez Git en ligne de commande, GitHub Desktop ou une extension dans votre éditeur.
    * Prévisualisez les modifications en local avant de publier.
    * Intégrez d&#39;autres outils, comme les tickets de support, le suivi des tickets et les systèmes de design.
  </Step>
</Steps>

<div id="core-git-concepts">
  ## Concepts fondamentaux de Git
</div>

<AccordionGroup>
  <Accordion title="Branche">
    Une branche pointe vers un commit précis dans votre dépôt. Votre documentation publiée est générée à partir d’une branche de déploiement. Vous pouvez avoir autant d’autres branches que vous le souhaitez avec des modifications qui ne sont pas encore publiées sur votre site de documentation. Si vous voulez intégrer les modifications d’une branche à votre documentation publiée, vous pouvez fusionner cette branche dans votre branche de déploiement via une pull request (PR).

    Utilisez les branches pour travailler sur des modifications sans affecter votre documentation publiée, tester de nouvelles fonctionnalités en toute sécurité et obtenir des retours avant la publication.
  </Accordion>

  <Accordion title="Cloner">
    Téléchargez sur votre ordinateur une copie complète d’un dépôt, y compris tous les fichiers et l’historique complet. Lorsque vous clonez un dépôt, vous obtenez tout le nécessaire pour travailler en local.

    ```bash
    git clone https://github.com/your-org/your-repo
    ```
  </Accordion>

  <Accordion title="Commit">
    Un instantané enregistré de vos modifications à un moment donné. Chaque commit inclut un message décrivant ce qui a changé et crée un enregistrement permanent dans l’historique de votre projet.
  </Accordion>

  <Accordion title="Conflit">
    Se produit lorsque deux personnes modifient différemment la même partie d’un fichier. Git vous demande alors de choisir manuellement quelle version conserver, ou de combiner les deux.
  </Accordion>

  <Accordion title="Branche de déploiement">
    La branche principale de votre projet. Les modifications apportées à cette branche sont automatiquement publiées sur votre site de documentation. Elle s’appelle souvent `main`, mais vous pouvez définir n’importe quelle branche comme branche de déploiement.
  </Accordion>

  <Accordion title="Diff">
    Un diff (ou différence) montre les changements entre deux versions d’un fichier. Lors de la révision de pull requests (PR), les diffs mettent en évidence ce qui a changé par rapport à la version d’origine du fichier.
  </Accordion>

  <Accordion title="Fusionner">
    Combinez les modifications d’une branche dans une autre. Cela se fait généralement via une pull request (PR) après révision, afin d’intégrer le travail sur une fonctionnalité dans votre branche de déploiement.
  </Accordion>

  <Accordion title="Récupérer">
    Récupérez les dernières modifications du dépôt distant dans votre copie locale. Cela vous permet de rester à jour par rapport au travail des autres.

    ```bash
    git pull
    ```
  </Accordion>

  <Accordion title="Pull request">
    Un moyen de proposer la fusion des modifications d’une branche dans votre documentation publiée. Elle permet une révision et une discussion avant la mise en ligne des changements. On l’appelle couramment une PR, et elle est aussi appelée merge request dans GitLab.
  </Accordion>

  <Accordion title="Envoyer">
    Envoyez vos commits locaux vers le dépôt distant. Cela rend vos modifications accessibles aux autres et peut déclencher des déploiements automatiques.

    ```bash
    git push
    ```
  </Accordion>

  <Accordion title="Distant">
    Une version de votre dépôt hébergée sur un serveur. Votre dépôt local se connecte à un dépôt distant pour envoyer et récupérer des modifications.
  </Accordion>

  <Accordion title="Dépôt">
    Le code source de votre documentation, avec tous les fichiers et leur historique, qui composent les pages de votre site de documentation. L’éditeur web se connecte à votre dépôt de documentation pour accéder au contenu et le modifier.
  </Accordion>

  <Accordion title="Indexer">
    Préparez des modifications précises à inclure dans votre prochain commit. La mise à l’index vous permet d’organiser les modifications en commits logiques.

    ```bash
    git add filename.mdx
    ```
  </Accordion>
</AccordionGroup>

<div id="how-the-web-editor-uses-git">
  ## Comment l’éditeur web utilise Git
</div>

L’éditeur web se connecte à votre dépôt Git via la [GitHub App](/fr/deploy/github) ou l’[intégration GitLab](/fr/deploy/gitlab), et automatise les opérations Git courantes.

Lorsque vous :

* **Ouvrez un fichier** : l’éditeur récupère la dernière version de votre dépôt, afin que vous travailliez toujours sur un contenu à jour.
* **Apportez des modifications** : l’éditeur enregistre vos modifications sous forme de brouillon, qui peut devenir un commit lorsque vous êtes prêt à sauvegarder votre travail.
* **Enregistrez les modifications** : l’éditeur crée un commit avec vos modifications, ce qui conserve votre travail dans l’historique du projet.
* **Créez une branche** : l’éditeur crée une nouvelle branche dans votre dépôt, que toute personne ayant accès au dépôt peut utiliser pour collaborer et relire les modifications.
* **Publiez sur votre branche de déploiement** : l’éditeur crée un commit et pousse directement sur votre branche de déploiement, ce qui publie immédiatement vos modifications.
* **Publiez sur d’autres branches** : l’éditeur crée une pull request (PR), ce qui vous permet de recueillir les retours d’autres personnes avant de fusionner vos modifications dans votre branche de déploiement.

<div id="common-workflows">
  ## Flux de travail courants
</div>

<div id="publish-directly-to-your-deployment-branch">
  ### Publier directement sur votre branche de déploiement
</div>

<Tabs>
  <Tab title="Avec l’éditeur web">
    1. Ouvrez le fichier dans l’[éditeur web](https://dashboard.mintlify.com/editor).
    2. Apportez vos modifications.
    3. Cliquez sur **Publish**.
    4. Les modifications apparaissent dans le dépôt et sont déployées automatiquement.
  </Tab>

  <Tab title="Développement local">
    1. Récupérez les dernières modifications : `git pull`
    2. Modifiez le fichier dans votre éditeur.
    3. Ajoutez les modifications à l’index : `git add filename.mdx`
    4. Créez un commit : `git commit -m "Update documentation"`
    5. Envoyez les modifications : `git push`
    6. Les modifications sont déployées automatiquement.
  </Tab>
</Tabs>

<div id="work-on-a-feature-branch">
  ### Travaillez sur une branche de fonctionnalité
</div>

<Tabs>
  <Tab title="Avec l’éditeur web">
    <Note>
      Pour créer des pull requests (PR) depuis l’éditeur web, vous devez avoir activé une règle de protection de branche imposant des pull requests avant de pouvoir fusionner des modifications dans votre branche de déploiement. Sans règle de protection de branche, les modifications apportées sur des branches sont fusionnées dans votre branche de déploiement lors de la publication.
    </Note>

    1. Créez une branche depuis le menu déroulant des branches dans la barre d’outils de l’éditeur.
    2. Apportez et enregistrez vos modifications sur la branche.
    3. Cliquez sur **Publish** pour créer une pull request (PR).
    4. Fusionnez la pull request (PR) lorsque vous êtes prêt.
  </Tab>

  <Tab title="Développement local">
    1. Créez une branche : `git checkout -b feature-name`
    2. Apportez et validez vos modifications.
    3. Poussez la branche : `git push -u origin feature-name`
    4. Créez une pull request (PR).
    5. Fusionnez la pull request (PR) lorsque vous êtes prêt.
  </Tab>
</Tabs>

<div id="review-changes-before-publishing">
  ### Passez en revue les modifications avant de publier
</div>

<Steps>
  <Step title="Créez une branche de fonctionnalité.">
    Travaillez sur les modifications dans une branche distincte de votre branche de déploiement afin de pouvoir les partager et les relire avant la publication.
  </Step>

  <Step title="Apportez vos modifications.">
    Modifiez les fichiers et validez les changements dans la branche de fonctionnalité.
  </Step>

  <Step title="Créez une pull request (PR).">
    Créez une pull request (PR) pour proposer la fusion des modifications de votre branche de fonctionnalité dans la branche de déploiement.
  </Step>

  <Step title="Passez en revue le diff.">
    Vérifiez vos modifications. La pull request (PR) affiche les différences ligne par ligne par rapport à la version d’origine du fichier.
  </Step>

  <Step title="Recueillez les retours de l’équipe.">
    Les membres de l’équipe peuvent commenter des lignes précises ou l’ensemble des modifications. Apportez les changements nécessaires et validez-les dans la branche de fonctionnalité.
  </Step>

  <Step title="Fusionnez après approbation.">
    Fusionnez la pull request (PR) pour publier les modifications dans votre documentation en ligne.
  </Step>
</Steps>

<div id="git-best-practices">
  ## Bonnes pratiques Git
</div>

Chaque équipe développe ses propres flux de travail et ses préférences, mais voici quelques bonnes pratiques générales pour commencer.

* **Rédigez des messages de commit explicites** : soyez précis sur ce qui a changé en utilisant un langage d’action. `Fix broken link in API docs` est plus informatif que `update page`.
* **Utilisez des noms de branche explicites** : les noms de branche doivent indiquer clairement leur objectif. Utilisez des noms informatifs comme `update-api-reference` plutôt que des noms génériques comme `temp` ou `my-branch`.
* **Gardez des branches ciblées** : veillez à ce que les modifications d’une branche restent centrées sur une tâche ou un projet précis. Cela facilite les revues et réduit les conflits.
* **Supprimez les branches après la fusion** : supprimez les branches lorsque vous n’en avez plus besoin afin de garder votre dépôt bien organisé.
* **Récupérez avant de pousser** : récupérez toujours les dernières modifications avant de pousser les vôtres pour éviter les conflits. L’éditeur web le fait automatiquement.
* **Vérifiez d’abord vos propres modifications** : consultez le diff avant de créer une pull request (PR).
